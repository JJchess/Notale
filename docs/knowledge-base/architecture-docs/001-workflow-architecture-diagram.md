# 🗺️ 给真实代码流水线画架构图的方法论

> **一句话版：** 架构图的价值不在"画得像"，而在**直接回答读者心里那几个问题**。先用子代理把代码事实挖干净，把用户的显式问题列成清单并**全部画进主总览图**（细节区只做展开），全程用自然语言术语、脚本校验禁用词，最后用无头浏览器截图放大逐区自检——这套流程一次到位，返工率最低。

---

## 🧭 TL;DR（给赶时间的人 / 给 Agent）

```
起点：架构图不是创作，是"代码事实 → 视觉语言"的转译；先调查，后动笔
核心：用户明确提出的问题 = 图的内容需求，且必须落在【主总览图】里，
      不能只写在下方详情区——第一版就栽在这，被点名返工
术语：严禁文件名/变量名/外部框架名（如 STORM）；
      建立"内部概念 → 学术/自然语言"对照表，grep 脚本兜底校验
版式：双泳道 + 蛇形流向 + 固定色彩语义 + 每步挂"提示词注入"虚线框；
      曲线/标签的碰撞要在坐标层面算一遍，别凭感觉
验证：Edge headless 截图 + ReadMediaFile 原分辨率局部裁剪看重叠和可读性；
      python HTMLParser 查标签闭合；grep 查禁用词。Windows 上零安装成本
禁忌：不要在没读代码的情况下凭印象画架构；不要把答案藏在表格里而主图不体现
```

---

## 🩻 背景

任务：为 `lecture-agent` 的讲义生成流水线产出一份清晰易读的架构图。用户给出的验收标准非常具体：

1. plan 阶段和 gen 阶段是不是两个独立 loop、如何桥接？
2. plan 阶段有哪些步骤、每步注入什么提示词、多视角是哪几个、串联还是并联？
3. 不许出现文件名/变量名/STORM 等内部或外部术语。

第一版的失误：**这些问题的答案写在了详情卡片和表格里，主总览图（overview SVG）里没有体现**。用户随即要求"所有我明确提到的问题都要体现在 overview 的图里面"。第二版把视角集群、每步提示词注入框、串并联标注全部画进主图后一次通过。

## 🔬 经验清单（按见效程度排序）

### ① 用户的显式问题 = 主图的内容清单，不是详情区的

- 把用户在需求里逐条列出的问题整理成 checklist，**逐条确认主总览图上能用眼睛直接找到答案**。
- 详情区（步骤卡片、产物表、提示词表）只做"展开证据"，不做"首次回答"。读者滚动到详情区时应该已经知道答案，只是在看细节。
- 判断方法：假装自己只看主图 30 秒，能否口头回答每个问题？不能就说明信息放错了层级。

### ② 先挖代码事实，再设计图——事实清单是图的合同

- 用 explore 子代理做一次 thorough 调查，产出结构化报告：阶段划分、每步的 LLM/确定性属性、提示词位置与大意、串并联关系、失败策略、产物与存储，全部带 `path:line` 引用。
- 把报告浓缩成"已探明的事实"清单写进计划，图的每个节点、每条边、每个标注都追溯到清单里的某一条。**图里没有一条不允许凭空出现的边**。
- 关键事实举例（这次调查改变了图的画法）：plan/gen 不是对等的双 agent loop，而是单向桥接；多视角是"单次调用内并列提出"而非多 agent 并行；生成路径上没有 LLM 评审回路——这三点全都成了主图的显性标注。

### ③ 术语转译：建对照表 + 脚本兜底，双保险

- 先建"内部概念 → 架构术语"对照表（如 skeleton → 讲义骨架、block → 内容槽位、fan-out → 有界并发填充），全文只用右列。
- 外部方法名（STORM）不直接出现，转译成功能性描述（"多视角覆盖规划法"）+ 视角角色的学术化命名（直觉引导者 / 理论推演者 / 实践建造者 / 质疑追问者）。
- 交付前跑一遍禁用词 grep（`STORM`、`\.py`、函数名、变量名），命中即改。人工自查必漏，脚本 5 秒钟。

### ④ 视觉编码：一套固定的语义，图例永远在场

- 色彩语义全程一致：泳道色区分阶段（紫=蓝图、绿=生成）、琥珀点=含模型调用、蓝点=纯确定性、红色=单向桥接、灰色虚线=可选/只读、琥珀徽章=自修回路（标注轮数上限）。
- 线型语义：实线=主数据流、虚线框=提示词注入、灰色虚线=可选路径。图例（fig-cap）必须和图同框。
- "每步注入了哪些提示词"用挂在步骤下方的虚线小框表达，用虚线短连线挂到对应节点——比塞在节点内部或角落注释里都清楚。

### ⑤ SVG 布局：蛇形泳道 + 碰撞要在坐标层面验算

- 两段式流水线用**蛇形（boustrophedon）布局**：上段左→右，桥接箭头在右端垂直下落，下段右→左。这样桥接线最短、不交叉，泳道标题注明阅读方向即可。
- 给"提示词注入框"预留专属水平带（主流程节点下方一整行），别事后见缝插针。
- 跨泳道的曲线（如只读核对回路）会和泳道副标题、注入框碰撞——**把贝塞尔曲线几个关键 t 值的坐标算出来**，确认不穿过任何文本框，再落笔。本次就是靠坐标验算发现并绕开了曲线与泳道副标题的碰撞。
- CJK 文本宽度估算：字数 × 字号 ≈ 像素宽，用于检查标签是否溢出容器。

### ⑥ 载体：单文件零依赖 HTML，复用仓库既有风格

- 内联 CSS + SVG，不引任何外部库/字体；交互用原生 `<details>`（点开看提示词细节），零 JS。
- 配色、导航、排版直接复用仓库里已有的架构文档（`docs/edumanus-arch-analysis.html` 的深色主题），新文档自然融入文档家族，也省一次设计决策。

### ⑦ 验证闭环：渲染出来看，不要信"应该没问题"

```
1. python HTMLParser  → 标签闭合、嵌套错误（10 秒）
2. grep 禁用词清单    → 术语纪律（5 秒）
3. Edge headless 截图 → 整页缩略图看结构（Windows 自带 Edge，
   --headless --screenshot --window-size 即可，零安装）
4. ReadMediaFile region 原分辨率裁剪 → 逐区查文字重叠、
   溢出、对齐（缩略图里看不见的问题全在这一步暴露）
5. 临时截图文件用完即删，不留在仓库里
```

## ✅ 给自动化流程的检查清单（画下一张架构图前过一遍）

- [ ] 已用代码调查（而非记忆/猜测）产出带 `path:line` 的事实清单？
- [ ] 用户的显式问题已列成 checklist，且**主总览图**能逐条直接回答？
- [ ] 术语对照表已建立；禁用词 grep 全绿？
- [ ] 色彩/线型语义有图例且全程一致？
- [ ] 每条跨区曲线做过坐标碰撞验算？每个文本标签估算过宽度？
- [ ] 单文件零依赖？风格与仓库既有文档一致？
- [ ] headless 截图 + 原分辨率局部裁剪自检通过？临时文件已清理？
