互动讲义的双轨结构

互动讲义是唯一具有两种完全不同渲染路径的内容类型：

路径触发方式渲染器文件
A: Chat PPT 对话内 ppt_result block PptDrawerContent (Drawer 内) chat/components/ppt-drawer-content.tsx
B: Course 播放器 course_gen_result → /courses/[id] react-pdf + WebAudio TTS (独立全屏) courses/[session-id]/page.tsx
注意：代码实验室打开 JupyterHub 不是直接使用 block 里的 browser_url， 而是每次先调用 POST /sessions/{id}/platforms/jupyterlab/open（同步等待，可能数十秒）拿到含 SSO token 的新 URL。 block 里缓存的 URL token 可能过期，不能直接 embed。
Part III

统一接口：共同输入与输出

共同需要的输入

从四种内容的实际消费方式归纳，它们的最小公共输入集合如下。 contentType 是判断分支的唯一键，其余字段按类型选填。

TypeScript — 共同接口（描述性，非实现）
// 所有四种内容共同需要的输入
interface InteractiveContentInput {

  // ── 会话身份 ──────────────────────────────
  sessionId:   string;          // 父 chat session
  toolCallId?: string;          // artifact 精确定位

  // ── 内容类型 ──────────────────────────────
  contentType: 'genui' | 'jupyterlab' | 'video' | 'ppt';

  // ── 展示 ──────────────────────────────────
  title?:  string;
  status:  'generating' | 'ready' | 'failed';

  // ── 类型专属（按 contentType 填其中一组） ──
  previewUrl?: string;          // genui: iframe src；video: playback_url
  pdfUrl?:     string;          // ppt: ppt_file_url[0]
  scripts?:    CourseScript[];   // ppt: 讲稿 + 音频
}

四种内容最终都在 LeftPersistentDrawer 内（或等效容器内）渲染， 生成中和完成后的渲染组件不同：

Part IV

是否适合作为 Flipbook 的一个 Page？

假设 Knowledge Palace 的每一页都是 <Page>…</Page>， 四种内容以直接嵌入 React 组件的方式存在于某一页中。 以下逐项评估当前状态下的可行性。

互动实验室
✓ 可嵌入
  • 嵌入iframe 已自包含，不依赖 Drawer 结构
  • 解耦重建轮询逻辑（genuiRebuildAbortRef）散布在 chat/page.tsx，需移入组件
  • 提升SnackbarContext 需在 Page 层之上提供
  • apiClient 需可达用于 /platforms/genui/preview 重建请求
  • 保留GenuiPreviewIframe 可直接作为 Page 内容
代码实验室
⚠ 需改造
  • 嵌入iframe 可用，但 URL 须预先通过 /open 换取
  • 解耦openedJupyter 状态 + jupyterOpening 状态在 chat/page.tsx，需提取为 hook
  • 提升apiClient 需可达，可能有数十秒等待
  • 去抖jupyterOpenAttemptedRef 防重复调用逻辑需一并迁出
  • 保留Jupyter 组件可直接用，缺的是"开容器→拿 URL"外壳
互动视频
✓ 最简单
  • 嵌入playback_url 直接 <iframe>，无需任何中间步骤
  • 解耦几乎无，视频 iframe 本身是完全外部应用
  • 提升无 Provider 依赖
  • 生成中GenuiProgressPanel 可作为 Page 内 loading 状态
  • 保留全部逻辑可迁移，结构最干净
互动讲义
⚠ 复杂
  • 两条路Drawer 内 PptDrawerContent 可提取；CoursePage 整体是 1760 行单体
  • 解耦CoursePage 须拆分（PDF渲染/TTS/ChatSidebar 各自独立）
  • 提升TTSContext 须在 Page 层之上；WebAudio 需宿主允许
  • 保留PDF 渲染逻辑（react-pdf）可直接作为 Page 内容
  • 注意wsClient 是模块级单例，多 Page 共存时需验证不冲突

需要解除的耦合

耦合点 当前位置 影响
openLeftDrawer 状态机 chat/page.tsx (openDrawers state) 四种内容的 open/close 逻辑必须在 /chat 内，Page 化后需由外层 Flipbook 接管
genuiRebuildAbortRef 重建轮询 chat/page.tsx 实验室 需将重建 abort 逻辑移入 GenuiPreviewIframe 或独立 hook

推荐的统一 Page API（概念层）

如果未来统一为 Flipbook Page，以下是最小公共接口的建议形态。无需现在实现。

推荐 Page API — 概念描述
interface KnowledgePalacePage {
  /** Flipbook 层管理的页码（用于翻页动画） */
  pageIndex: number;

  /** 页面类型，决定渲染组件 */
  kind: 'genui' | 'jupyterlab' | 'video' | 'ppt' | 'markdown' | 'quiz';

  /** 内容来源：已完成的 artifact */
  artifact: {
    sessionId:   string;
    toolCallId?: string;
    contentUrl?: string;   // genui preview_url / video playback_url
    pdfUrl?:     string;   // ppt ppt_file_url[0]
    scripts?:    CourseScript[];
  };

  /** 显示 */
  title?:    string;
  thumbnail?: string;

  /** Flipbook 层注入的回调 */
  onNext?:   () => void;
  onPrev?:   () => void;
  onReady?:  () => void;   // 内容加载完成后通知 Flipbook 可翻页
}
wsClient 单例注意事项： 当前 wsClient 是模块级单例（lib/api/websocket-client.ts）， 在 Flipbook 中多个 Page 可能引用不同 sessionId。 多 Page 共存时需验证 connect/disconnect 的生命周期不互相干扰， 或考虑将 wsClient 改为按 sessionId 实例化。
