id: S-014
title: runnable stays cold after D-008; a second copy of the quantity cap was found but does not fully explain it
kind: observed
context: A cross-project audit of viewer/telemetry/coverage.json (66 historical real-generation runs) found `runnable` fired only 3 times total (engines custom×1, objective1d×2), far colder than `code` (37). This is after D-008 (2026-07-20) already removed the "0-2/别过量" quantity cap from planning.py's hand-written skeleton guidance.
trigger: Found a second, un-removed copy of near-identical quantity-cap language ("keep the whole deck to roughly 0-2 runnables" / "全课 0-2 个，别过量") living in `skills/create-code-runtime/SKILL.md`'s body (line 18) and `contracts.json`'s trailing comment (line 2) — the natural hypothesis was that D-008 fixed one copy and missed this one, explaining continued coldness. On closer inspection this hypothesis only half holds: `lecture_agent/domain/skills/registry.py:55` parses ONLY SKILL.md's frontmatter, never its body — the body text was never seen by any model call. `reg.contract` (contracts.json's content) is injected only at fan-out time (`agent/orchestrator.py:115,259`, inside `domain/generation/blocks.py:78`'s per-block prompt) — AFTER a runnable placeholder is already scheduled in the skeleton, never at the plan/skeleton stage that decides whether to include one at all. `AUTHORING_RULES` (the global hard-rules block that DOES reach the skeleton prompt) contains no runnable-related cap either.
bad_outcome: The plan-stage skeleton prompt for runnable was therefore already fully clean of quantity-suppression text after D-008 alone. Removing the second copy (this scenario's fix, M-014) is legitimate cleanup — consistent phrasing, and it may still affect fan-out-time authoring richness for an already-chosen runnable block — but it does NOT explain, and is not proven to fix, why the skeleton rarely chooses to include a runnable placeholder in the first place. That root cause remains genuinely open: plausible candidates are topic-fit (fewer topics have as natural an "edit-and-run" moment as a sim/animation) or the model's own prior favoring visual/animated interactivity over a code-editing prompt — neither is fixable by further prompt-text edits alone.
why_it_matters: A plausible-sounding "found the duplicate, removed it, bug fixed" narrative would have been wrong here — the duplicate was real but not causally connected to the observed symptom via the code path actually taken. Scenarios must trace the actual data flow (what a model call actually receives), not just grep-match a suspicious phrase across files.
status: open

## Notes
