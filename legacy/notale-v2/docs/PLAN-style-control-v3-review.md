# 风格控制升级：v3 审阅与建议方案

2026-09-08。状态：研究留档，尚未实施。**实施建议已由[风格控制升级方案·收敛版](../../../notale-v2/doc/PLAN-style-control.md)取代**；本文第 1、2 节保留现状审阅与上游研究，第 3–9 节为历史提案，不再作为实施依据，尤其不再采用 style.json 与主题编译器。审阅对象为当时工作树的 [v3 架构图](../architecture/ARCHITECTURE-v3.html)、[媒体与主题包计划 v2](PLAN-media-template-v2.md)及实际生成链路。

核心判断：v3 是合理的「用户参考与底图接入」方案，但尚不足以成为多风格控制系统。应保留三个角色与现有页面生成能力，把 Director 的交付升级为**可执行的风格包：视觉参数、使用规则、少量可复用样式、背景变体和视觉示例**。Builder 仍决定本页如何表达内容。

## 1. 现状审阅：哪些保留，哪些必须改

### 1.1 v3 值得保留的决定

- Planner 管内容证据，Director 管外观，Builder 管页内构图；图片按用途区分，整幅地图仍可属于证据。
- 原图保留，底图与蒙版只合成一次，logo 独立；内容可覆盖装饰底图。
- 用户参考优先于默认审美；技术错误和设计偏好分开处理。
- 不把复杂图片背景上的统计值冒充逐字可读性证明。
- 使用 run 目录和现有编排，不增加服务、角色、消息总线或通用页面 DSL。

### 1.2 主要缺口与影响

| 优先级 | 证据与问题 | 对目标的影响 | 建议 |
| --- | --- | --- | --- |
| P0 | [style-theme](../../../notale-v2/prompts/style-theme.md)禁止面 token、边框、圆角、阴影等；[director.gates](../../../notale-v2/core/director.py)实际检查 SHAPE、SURFACE、SURFACE_WORDS | 纸张拼贴、玻璃、粗边框、卡片式品牌等无法成为稳定主题；「材质」一句话无法补足实现 | 放开合法视觉能力，以作用范围和主题规则约束；不再按形态名称一票否决 |
| P0 | 原计划只承诺颜色、字体、底图、角标、说明，明确不包含版式组件系统 | 解决品牌元素接入，但页面仍可能只有换色区别 | 增加构图语法和视觉元素 recipe；不需要先建整套固定版式库 |
| P0 | [scrub-theme-slop](../../../notale-v2/workflows/scrub-theme-slop.md)、[scrub-visual-slop](../../../notale-v2/workflows/scrub-visual-slop.md)、[tech](../../../notale-v2/prompts/tech.md)还有渐变、光晕、纹理、装饰、标题处理等限制 | 即使 Director 接受风格，Builder 也可能按另一套要求消除它 | 对所有风格入口统一优先级；同步修改实际注入内容，不能只在主题末尾补一句「用户优先」 |
| P0 | 单个 backdrop 与全局 token 没有页级模式、前景配对、裁切焦点或避让区域 | 封面照片被铺满所有正文页；换浅底后仍用浅字；文字压住主体 | 增加 background variant、配套前景色与使用规则 |
| P1 | [gallery.index_text](../../../notale-v2/core/gallery.py)主要提供标题和颜色，选样强制跨三个明度档；下一步才看截图 | 第一步没有足够证据选字体、构图、材质；固定品牌要求也可能被无关参考稀释 | 给画廊补少量可观察的视觉特征和多页预览；跨明度档改为探索策略 |
| P1 | [builder.shared_preload](../../../notale-v2/core/builder.py)仅给视觉页主题 INTERFACE；参考截图跟随 Builder 还是默认关闭的实验开关 | Director 看过的视觉信息变成几句文字后丢失，并行页面各自解释风格 | 每套提供精简共用风格说明和代表性样张，按页发送相关背景信息 |
| P1 | [build-code 分支](../../../notale-v2/core/builder.py)隔离主题；[代码宿主](../../../notale-v2/core/code_runtime.py)固定深底，并使用独立 iframe | 「全套换风格」实际上跳过代码页，外部 CSS 也不能穿透 iframe | 在宿主侧增加受控的代码主题适配，先支持背景、字体、强调、边线与状态色 |
| P1 | [selfcheck](../../../notale-v2/vendor/chassis/selfcheck.py)的次级文字统计使用 stage 背景，透明背景按白色计算 | 不能用它证明图片、半透明面或局部深浅区域上的对比度 | 保留原统计用途；另报告对比检测覆盖范围与未测区域 |
| P1 | 现有检验重点是色彩分布、完整性和技术错误 | 不会发现「所有主题都长成同一种卡片」或「只有封面忠实」 | 增加同内容跨风格、同风格跨页型的渲染比较 |

额外的不一致：[scrub-theme-slop](../../../notale-v2/workflows/scrub-theme-slop.md)把奶油配色描述为组合问题，并允许纸张/手稿等题材例外；`director.gates()`却只凭底色命中 `is_cream()` 就拒绝。灰阶也从提示词的「全死中性」变成代码中的两个中性 token 即拒绝。应消除这种策略与执行的偏差。

原 B/C 尚未实施：当前 `direct()`仍只调用 `pick()`和 `theme()`，后者只有 Write 工具；当前 Director CLI 没有 `--template`。因此架构图中的主题包和取底图是待建能力，不是现有行为。

## 2. Dashi 的风格控制是怎样实现的

研究固定在上游提交 `7cb23347f91cda1a5519eafc8c040704e389535a`。用户提供的旧仓库地址当前重定向到 `chuspeeism/dashi-ppt-skill`。下面基于源码和仓库内预览图；没有运行其完整生成、编辑或导出流程。

### 2.1 可以核实的结构

| 层 | 源码行为 | 对 Notale 的启发 |
| --- | --- | --- |
| 主题选取 | 通过 `themePack`选择主题；元数据登记风格、适用场景和该主题拥有的 layouts | 风格、风格内配色、版式应能分别表达 |
| 预制页 | 每个主题有自己的页面组件、默认 props、内容槽与 controls | 多样外观来自实际渲染实现，不能只依赖一个风格名称 |
| 主题适配 | adapter 把原始主题整理成字体阶梯、间距、圆角、阴影、card/media/chart/shape treatment | 风格必须影响文字、形状、图表和图片的具体处理 |
| 背景变体 | `getBespokeThemeProfile(themeKey, background)`合并语义背景与配套前景；包含 default/surface/muted/accent/dark/light 等 | 切换背景要同时切前景，不能只换一个 `--bg` |
| 自定义构图 | BespokeSlide 使用主题 profile、构图 family 和元素类型渲染；部分 adapter 定义 familyRecipes | 可以让内容构图自由，同时绑定同一种视觉语言 |
| 图片处理 | MediaElement 读取主题的 radius/filter/border/overlay，内容指定 src 与 cover/contain | 图片的取材和视觉呈现应分工 |

源码：[主题登记与预制页入口][d-registry]、[预制页元数据][d-metadata]、[profile 合并逻辑][d-core]、[BespokeSlide 渲染][d-render]。

代表性差异：theme03 为不同构图显式定义页框、标题尺度与列表处理，主打直角、无阴影、开放式承载；theme05 有纸张色、色谱与细线处理；theme09 的 adapter 定义半透明面、模糊、圆角和图片蒙版。它们同时改变多个维度。[theme03][d-03]、[theme05][d-05]、[theme09][d-09]。

### 2.2 借鉴时也要批评

1. **不要把所有效果归因于一个 schema。** 大量差异来自各主题的预制源码。引入同名字段，并不会自动得到同等外观质量。
2. **自定义路径仍有同构风险。** `DEFAULT_FAMILY_RECIPE`默认使用 cards；本次查看的 adapter 中 theme02、theme03 明确定义 familyRecipes，其余多依赖默认值。统一渲染器会降低维护成本，也可能抹平布局差异。这是源码揭示的风险，未经跨页渲染测量，不能据此断言所有实际成品同质化。
3. **不能把语义背景当作完整的图片背景协议。** `composition.background`选择的是 profile 变体，MediaElement 实现的是内容媒体槽；这两段代码并未构成我们需要的全套底图选择、焦点裁切、logo 分层和失败处理闭环。
4. **Notale 的内容不是只填槽的汇报稿。** 算法交互、Canvas 实验、3D 与代码工作台需要自己的结构；不宜迁移为固定 12×8 元素布局或只允许受限 composition。
5. **预览图必须区分用途。** 仓库的 [风格总览图][d-grid]有明显视觉差异，但文字多为示意色条；它能用于辨识风格，不能证明中文正文、公式和复杂交互的可读性。

结论：吸收它的「主题适配 + 视觉 recipe + 变体」思路，由 Notale 自己实现适合教学页面的风格资源。无需引入对方 runtime。

## 3. 升级后的能力范围

风格至少覆盖以下维度，字段按主题需要出现；不要求每次填满所有可能参数。

| 维度 | 可控制内容 | 边界 |
| --- | --- | --- |
| 色彩 | 画布、承载面、前景配对、品牌强调、图表序列、交互状态 | 品牌色、数据概念色、交互状态色分别命名；用文字/形状辅助表达状态 |
| 字体与排版 | 中英文字体、标题/正文/数字字阶、字重、行高、字距、标题对齐 | 不靠缩小正文解决内容溢出；字体必须能加载且覆盖所用文字 |
| 构图语法 | 留白密度、非对称倾向、标题层级、图片出血、图注关系、页间节奏 | 不为每页预先指定固定列数或矩形坐标 |
| 形状与材质 | 圆角、描边、线宽、阴影、玻璃、纸纹、标记与连接线语言 | 数据几何和逻辑拓扑不因风格改变 |
| 元素 recipe | 标题、注释、引语、数值、图例、控件、面、图片的可复用样式 | recipe 是实现方法；内容分组不自动变成卡片 |
| 图片语言 | 摄影/插画倾向、裁切、边框、色调、图注、蒙版 | 证据图保持可辨识，禁止风格化改变数据或来源含义 |
| 背景系统 | 纯色、渐变、纹理图、全幅照片、局部图片、同主题多个变体 | 原图保留，内容可覆盖装饰层，切换背景同步前景 |
| 动效 | 节奏、时长、缓动、强调方式 | 遵守 reduced-motion；不改变教学步骤和计算结果 |
| 品牌元素 | logo、位置、尺寸、净空、必要固定标题区 | 净空可执行；精确复刻任意 PPT 母版另属能力 |

入口统一为：内置风格、自然语言要求、用户参考包。用户只有一张图片或一句「粗边框拼贴风」也应能进入；完整风格包不强制有截图。截图是参考，不默认充当背景。

优先顺序：功能与可读性要求 → 用户明确约束 → 选定风格包 → Director 对模糊要求的解释 → 默认设计偏好。用户要求之间冲突时记录具体冲突，能通过布局或遮罩解决的直接解决；无法满足的明确报告。

这个优先级必须反映在实际生成的提示词和校验配置中。米色、灰阶、玻璃、渐变、卡片与纹理可以作为正常选项；无用户主题包的自动风格也不应永远受旧审美黑名单限制。

## 4. 推荐架构与交付契约

### 4.1 流程与三个角色

1. harness 解析用户的风格意图、参考与可选本地资源，得到可加载输入和明确约束。
2. Planner 继续规划内容与证据；Director 同时选视觉参照、获取必要装饰图。已有完整风格包时跳过重新选样。
3. Director 写最终风格时，可读取已完成的页表摘要和采用素材的用途上下文，完成字体、概念色及变体规则。不要逐页规划坐标。这样能知道本套有公式、照片还是高密度实验。
4. harness 校验并解析资源，确定性生成运行用主题、说明和共享图示，冻结后再发给各页 Builder。
5. Builder 依据本页内容选背景变体和 recipe，实现与检查；共享产物不由页级并发任务覆盖。
6. 批次终止后检查实际页面，并汇总完整性、主题一致性、图片使用和可读性覆盖。

第 3 步是有意调整当前「双方互不看输出」：保留前段并行，Director 的最终主题调用等候页表。它复用已有写主题调用，不必另加一个协调 agent 或固定审美复核循环。代价是可能延后主题定稿；实验单独记录关键路径耗时。完整且无需内容适配的固定品牌包可以直接编译。

不要求 Planner 增加一整套样式字段。页表仍保留其现有内容契约；Builder 可以从本页 brief 选择合法变体。章间过渡、照片页等视觉用途不等同于现有四种 workflow 路由标签。

### 4.2 一个源，多个派生产物

建议新增 `style.json`作为 run 内解析后的唯一配置源，`theme.css`继续作为运行接口。机器字段只存需要执行的值；构图意图等开放内容以短文本保存，不把所有设计判断枚举成 DSL。

| 产物 | 作者/来源 | 消费者 |
| --- | --- | --- |
| `style.json` | Director 输出，经 harness 校验与资源解析 | 编译器、审计、以后重新使用风格 |
| `pages/assets/theme.css` | 确定性编译 | base.css、HTML/SVG、Builder 可读接口 |
| `pages/assets/style-guide.md` | 从同一配置生成 | Builder 共用说明；含允许变体、recipe 和使用规则 |
| `pages/assets/style/…` | harness 导入的图片、字体、logo、预览 | 页面、主题样式、视觉输入 |
| 原运行报告中的 `style` 小节 | 编排与检查汇总 | 用户与实验分析 |

不要让模型分别写 JSON、CSS 和接口注释中的同一组值。`INTERFACE`也由源配置生成，避免显示的契约与实际 CSS 不同。原 `--bg / --text / --font-sans`保留为兼容别名。

用户包建议采用 `STYLE.md`、可选 `style.json`、`shots/`、`assets/`。继续支持原 `shots/backdrop/logo/fonts/TEMPLATE.md`目录，导入时统一。结构化包至少有有效风格配置；截图包至少有一张可读参考图；仅文字要求可不建包。未知字段/版本应报错，未提供的可选维度从明确的基础风格继承。

顶层契约建议如下；输入包可以省略可选值，run 内保存解析后的完整快照：

| 配置区 | 保存什么 | 最小校验 |
| --- | --- | --- |
| `schemaVersion / id / version` | 协议与风格版本 | 支持的版本、有效标识；复用时固定版本 |
| `intent / constraints` | 视觉论点、用户明确要求、可调整范围 | 原要求与推导选择分别记录，不能反向覆盖用户要求 |
| `tokens / typography` | 色彩角色、配套前景、字体资源、文字层级、间距、形状与动效参数 | 类型/单位有效，引用存在，无循环，必要兼容 token 完整 |
| `grammar / recipes` | 构图语法、元素样式与适用条件 | recipe 引用有效，样式作用域受限；不包含内容数据或全页坐标布局 |
| `backgrounds / defaultBackground` | 背景层、文字区、回退和使用规则 | 默认及回退存在，回退无环；opacity/position/区域范围有效 |
| `brand / assets` | logo 净空与位置、实际资源路径、来源 | 资源在 run 范围，声明与可加载文件一致 |
| `adapters` | HTML/SVG、Canvas/图表、代码宿主的受控映射 | 不支持的能力明确列出，不能默默丢弃 |

解析顺序是基础风格 → 用户覆盖 → 选定背景变体 → 被允许的页级局部调整。用户锁定项始终保留；对象按字段合并，列表整体替换，缺值表示继承，显式关闭用 `enabled:false`。不允许隐含的多层继承链；展开后的 run 快照不依赖外部包的后续变化。编译前验证资源和结构，编译后用浏览器验证 CSS、字体和最终层合成，不能把现有正则 gates 当作完整 CSS 校验器。

### 4.3 recipe 与样张怎样避免失控

- recipe 同时给出名称、用途、允许场合、具体样式和一个小示例。例如「细线图注」绑定字体、线宽和间距；「玻璃交互区」绑定面色、边框、模糊与前景。
- 共享 CSS 只作用于显式 `.nt-*`类或约定的 `data-*`节点。禁止宽泛地覆盖所有 `div`、`svg`、`button`或第三方库内部选择器；不改画布缩放和指针机制。
- 模型生成的新 recipe 通过受限的样式属性与声明式装饰层表达；复杂装饰可导入图片/SVG。SVG 是实际新增的导入能力，需要资源有效性处理；不要直接假设现有 raster 解码器能接受。
- 不注入任意第三方 JS 主题运行时。内置复杂样式使用项目维护的实现；单页特殊结构仍由 Builder 实现。
- 共享样张至少体现正文与主视觉的关系。只有封面参考时，可提炼方向，但明确正文规则由 Director 推导；不能声称正文忠实复刻。
- 画廊补充可观察的字体类别、图片占比、空间密度、边框/阴影/纹理、构图特征。特征用于召回；截图与用户要求用于判断。不必建庞大的流派分类器。

## 5. 图片背景的完整设计

### 5.1 用途先分清

`reference`是只看不渲染的参考；`decorative`是可弱化/覆盖的装饰；`evidence`承担内容事实；`brand`是 logo 等固定元素。同一文件可以出现在不同用途，但每个使用处的规则必须清楚。

Director 管装饰与品牌；Planner/Builder 管证据。无需给旧的 `media_by_page`强加一套必填元数据：本次新增的用途和合成参数集中在主题背景定义中，已有证据映射继续使用路径。

### 5.2 背景配置示例

下面是建议的 `style.json.backgrounds`片段，**仅展示协议，不是已有可执行配置**。`path`以 `pages/`为根，图片必须已经导入成功。每个变体可以有多个装饰层，顺序从后到前。

```json
{
  "defaultBackground": "reading",
  "backgrounds": {
    "reading": {
      "fill": "#F3F0E8",
      "foreground": { "text": "#202722", "muted": "#505B53" },
      "layers": [],
      "usage": "正文、公式和密集图表"
    },
    "photo-opening": {
      "fill": "#14221A",
      "foreground": { "text": "#FFFFFF", "muted": "#E1E9E3" },
      "layers": [{
        "kind": "image",
        "path": "assets/style/forest.jpg",
        "role": "decorative",
        "fit": "cover",
        "position": [0.72, 0.45],
        "opacity": 1,
        "overlay": {
          "kind": "linear",
          "angleDeg": 90,
          "stops": [[0, "#101B13", 0.82], [1, "#101B13", 0.12]]
        }
      }],
      "contentZones": [{ "x": 0.06, "y": 0.12, "w": 0.43, "h": 0.70 }],
      "fallback": "reading",
      "usage": "开篇或照片主导页；正文优先使用左侧区域"
    }
  }
}
```

`position`是归一化 object-position，而非已经验证的主体坐标；`contentZones`是逻辑画布中的归一化建议排版区，不是对比度保证。为必要品牌净空另设必须避让的 `reservedZones`。fit 包括 cover/contain；纹理重复使用独立的 repeat 与 tileSize，不让照片意外平铺。

只需要纯色的主题可以完全没有图片层；渐变可以由 fill 的结构化变体表达。前景配对还应覆盖图表轴线、焦点环、承载面文字等实际使用角色；示例为简写。

### 5.3 渲染与覆盖规则

层次为：基础底色 → 装饰图片/纹理 → 装饰蒙版 → 内容 → 独立品牌层。背景、内容与 logo 均在同一缩放画布坐标内；背景和品牌装饰层不拦截鼠标事件。系统创建固定层节点，Builder 在专用内容节点内实现页面；Canvas、SVG 和交互指针坐标必须回归检查。

`html`根节点显式选择 `data-background`；未指定时使用 reading 等该主题的正文默认值。当前 `Deck.token()`读取 `document.documentElement`，所以全页变体 token 必须定义在这里；只把变量放在 `#stage`会造成 Canvas 与 DOM 读到不同颜色。局部反色区域需要显式把配对值传给图表/Canvas，不假定全局读取能获得局部样式。`data-backdrop="off"`只关闭装饰层，继续保留品牌与适用前景配置；Builder 铺全幅证据时必须声明对应的前景处理，不能继承不适配的颜色。由生成器提供默认值和合法值列表，避免模型猜类名。

CSS URL 必须由编译器按 CSS 文件所在位置重写：例如配置的 `assets/style/forest.jpg`在 `assets/theme.css`中应指向 `style/forest.jpg`。HTML 与 CSS 的路径基准不能混用。

导入时保留源文件与来源记录，生成必要浏览器资源；原图不先压暗、不永久烘焙文字或 logo。可下载或生成一个无文字背景，标题与教学信息保持 DOM/SVG，可编辑并可被检查。

### 5.4 可用性与失败行为

- 取图复用 `core/media.py`；给 Director 接入实际工具循环，返回图片后才能决定采用，替换时不保留旧引用。
- 用户明确指定的背景/字体/logo缺失，报告具体未满足要求；不能静默换成任意资源后宣称完整完成。自动选择的可选装饰失败时，用声明的 fallback，并记录降级。
- 资源检查包括路径范围、解码、宽高、字体加载和引用完整性；保留现有来源记录，不建设新的素材服务。样式包携带的资源复制进 run，保证离线及复用。
- 局部文字难读时依次考虑换裁切、移文字、用局部渐变、用该主题的承载面或改背景变体。不要预先统一压暗所有图片。
- 实际检查看下载与渲染两个层面：CSS 背景也须完成加载并有可见面积；不能只统计 `<img>`或请求成功。所有步骤可见状态都应纳入截图检查。
- 纯色区域报告可测对比；图片、混合与模糊区域标记未覆盖，结合截图复核。建议普通文字以 4.5:1 作为内部目标；这是本方案验收目标，不声称旧 Check 已支持。
- 品牌净空与内容发生冲突时优先重新排版；如果必需品牌位置与必需内容确实无法兼容，报告冲突，不能直接隐藏 logo。

## 6. Builder、图表和代码页怎样使用

同一 workflow 的共用前缀包含冻结的风格说明、完整变体规则和 recipe 索引；不要把每页不同的背景裁切写进共用前缀。首条 user 消息包含本页内容、相关媒体与已选背景预览。按能力传视觉图；不支持图像输入的模型明确只获得文字约束，不能把它当成看图验证。

页级背景由 Builder 选择时，首条消息先提供候选及缩略图，最终选择写入页面根属性，不假设 harness 已知道未发生的选择。主题只给少量当前风格的有效候选；构建记录和 Check 从实际 HTML 读取结果。每套的共用风格样张固定，避免把整个画廊再次发给每页。

HTML/SVG 用 scoped CSS 和 token；Canvas/WebGL 与图表用同源生成的颜色、字体、线型配置，利用已有 `Deck.token()`等接口。图表 recipe 只改变字、线、点、面和图例处理，不改数据、刻度含义或网络拓扑。跨页同一概念的颜色绑定放在整套风格配置中，Builder 不逐页重命名。

代码页在宿主侧接入受限适配：编译一份代码皮肤进入 iframe，映射字体、编辑器明暗、背景、边线、强调与状态色；保持工作台布局、交互和运行协议。外部 theme.css 不能直接继承进 iframe；[当前宿主固定深底](../../../notale-v2/core/code_runtime.py)要一起调整。复杂照片、装饰纹理默认作用于代码页外壳/说明区域，编辑器与输出区保持清晰承载面。预览和交付需说明这一适配范围，不能把它称为任意风格完整复刻。

换风格后的处理分两级：同一结构下改配色、背景与受控参数可重新编译；换字体尺度、构图语法或跨风格族需要重建受影响页面并复查。已经生成的任意 HTML 不能承诺只替换 CSS 就完成结构换肤。

共享资源在 Builder 开始前冻结。改主题后派生文件和共用前缀统一更新，旧页面重建或明确标记待更新；不在并行建页过程中覆盖共享 CSS。

## 7. 首批风格与视觉验证

建议第一批覆盖六个相互拉开的风格族，每套至少有开篇、正文/图表、交互及代码适配的实页证据。风格数量是首批内容建设目标，不成为架构上限。

| 风格族 | 非颜色差异 | 背景与内容规则 |
| --- | --- | --- |
| 研究编辑式 | 衬线/无衬线组合、非对称标题、细线图注、开放排版 | 纸纹可选；正文保持可读的纸面 |
| 技术图谱式 | 等宽标签、直角、明确连接线与刻度、紧凑但分层 | 低噪声底；坐标网格与装饰分开 |
| 玻璃光感式 | 半透明面、圆角、层次阴影、平缓转场 | 局部图像/渐变；文本承载面有稳定前景 |
| 粗边框拼贴式 | 粗线、硬阴影、贴纸/裁切、强标题比例 | 纸片/照片局部拼贴，不盖数据与操作 |
| 摄影纪录式 | 大照片、出血构图、短图注、留白随主体位置 | 封面或重点页照片背景；密集页用安静变体 |
| 水墨书卷式 | 中文标题字体、墨线、章印式强调、疏密对比 | 宣纸/水墨资源；公式和图表不用破损字形 |

这六套是 Notale 的拟议方向，不是对 Dashi 六个主题的一一复制。每套也需要至少一个不用卡片的正文 recipe，卡片风格可以存在但不应垄断所有页型。

判断「不只换颜色」：同一事实和数据换风格后，至少能观察到字体层级、形状/材质、构图/图片处理三个非颜色维度的变化。灰度图可辅助隔离配色影响，但不能作为唯一判据。

## 8. 实施顺序与完成标准

| 阶段 | 具体改动位置 | 交付与退出条件 |
| --- | --- | --- |
| S0 冻结基线 | 当前 prompts、gates、代码宿主及代表性运行产物 | 记录实际版本与现状截图；当前 dirty worktree 不能只用 git HEAD代表基线 |
| S1 风格源与策略 | `core/director.py`、`core/planner.py`、`core/skills.py`、style/deck/tech prompts、两个视觉 scrub 文件 | 建立最小 style.json 与编译；三个入口共享优先级；米色、灰阶、玻璃、粗边合法，非法资源仍拒绝 |
| S2 背景纵向贯通 | Director 取图、导入/编译辅助模块、chassis 层节点、Builder 接口、Check | 一套含照片背景的风格跑通；裁切/前景/fallback/logo/全幅证据/离线真实验证 |
| S3 多维风格资源 | 六套风格、recipe、小样张、画廊特征、图表适配 | 同内容跨六风格实页成立；正文和交互不会全部退成相同卡片 |
| S4 全链路与默认切换 | 代码宿主适配、构建交接、旧入口迁移、全套回归 | 四个 workflow 均有明确风格覆盖；重建与降级状态准确；完整 deck质量通过后启用新默认 |

S1–S4 合起来才是此次升级的完成状态。S2 只是可验证的纵向里程碑，不以「背景能显示」代替全部目标。可以先做新 `style-v2`实验路径，保留旧 run 的读取；验证后统一新生成默认入口，避免 Planner 自写主题和独立 Director 两套标准长期分叉。

最小但有区分力的验证组合：

- **契约/策略**：显式灰阶、米色、玻璃、粗边框分别可用；token/接口同源；非法路径、悬空资源、未知背景、无效字体可定位；覆盖所有真实入口及 Builder 注入。
- **背景运行**：浅图深字、深图浅字、复杂照片、纹理、关闭装饰、独立 logo、全幅证据、字体失败、背景失败、离线打开。检查加载、可见面积、裁切和交互点击。
- **同内容跨风格**：冻结五个页面任务——标题、文字/公式、图表、交互、代码；六套风格共 30 页。事实与数据不变，人工对照截图和实际操作，检验非颜色差异与主题忠实度。
- **同风格跨题材/全套**：从历史、生态、算法中选两套完整内容，至少一个照片主导主题和一个非照片主题；检查页间节奏、重复构图、语义色绑定与所有重要交互状态。
- **成本与稳定性**：记录 Director/Builder 调用与修订数、失败/降级、端到端耗时、缓存、token；不同提供商计量口径分开。质量判断不由成本平均值代替。

上线验收必须分别给出：技术通过、风格规则符合、资源真实呈现、内容/交互保持、图片文字区域的检查覆盖。任一页存在已知严重不可读、品牌冲突或交互失效时不能用整套均分掩盖。纯结构检查、图片数量和一张漂亮封面都不足以证明完成。

## 9. 对 v3 图的具体修订建议

本次只提出修改，不更改现有图的实施状态。

- `--template`输入改为「风格意图 / 参考包 / 内置风格」，底图、logo、字体仍是资源输入；截图与可渲染素材区分。
- 「①选参照 + 可选底图」保留，增加对非颜色特征的选样；现有跨明度约束降为策略。
- 「②看图写主题」改为「定风格包」，交付 style.json，包含 token、recipe、变体及规则；从 Planner 摘要加一条必要信息输入。
- 「主题层·单次合成」改为「校验 / 编译 / 冻结」，输出 theme.css、风格说明和资源；仍坚持原图与单次蒙版。
- Builder 输入明确共用风格语法、样张及本页背景选择；添加代码宿主的受控主题适配。
- 最终审计增加多维风格与背景覆盖，区分不可测区域，不把当前次级文字指标当全页对比验收。

这版方案的主要扩展是把「支持一种风格」定义为一组能运行、能复用、能验证的视觉决定；它仍不承诺任意 PPT母版解析、浏览器内完整样式编辑器或已生成页面无损实时换风格。
