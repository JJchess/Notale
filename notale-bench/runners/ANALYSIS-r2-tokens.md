## page-09 在干什么

76 次调用 = Read 15、Write 1、Check 29、Patch 28（含 5 次 Patch 没命中）。第 2 到第 74 步是同一个循环：

    Patch（挪"柱体上方数值标注"或"50% 半值阈值参考线 (1.02%)"）→ Check → 报叠压 → Patch 同一处 → Check → …

两处目标被反复 Patch 各约 12 次。模型每次只挪几像素，selfcheck 每次都判叠压，没有任何一方退出。

三个观察：
1. **harness 没有振荡检测。** 同一个 `old_string` 目标被 Patch 第 3 次时就该停：要么放弃这个装饰（删掉数值标注），要么接受当前状态收尾。现在的"最多 11 次响应"只是提示词软目标，harness 事后记录不拦截。
2. **打转的对象是编出来的图。** 那条 1.02% 参考线和柱上数值都不在材料里（PresentBench 忠实项对这一页也判否）。不该存在的元素既丢忠实分又烧 token。
3. **Read 15 次**里大半是在循环中途重读页面源码找行号——Patch 没命中后的补救。Patch!miss 5 次都出在这页。

## 对 dev 上容错/省 token 工作的建议（只是建议，不动 harness）

- 按 Patch 目标去重计数，同一目标 ≥3 次即终止本页的修补循环，标 `oscillation`，保留当前产物。预计这一套省 60% 以上输入 token。
- Check 报叠压时附上"删掉该元素"作为合法出口，而不是只给坐标。
- 图表数值必须有来源（`<sources>` 或 media 数据文件）；没有来源的图退成无刻度示意。这一条同时修忠实分和长尾循环。

对照：r1 26 页只出 11 页，花了 359 万；出片的页页均 30–60 万，那是 Builder 直接 Read 17 万字符材料的账，已由 `sources_by_page` 消掉。r2 页均 51 万看着更高，但 66% 集中在 5 页长尾，去掉长尾后页均约 22 万。
