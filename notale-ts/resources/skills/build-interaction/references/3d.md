# Consequential 3D Interaction

The learner's spatial action must change the model or its evidence. Orbiting a decorative object is inspection, not the learning loop.

## Require a spatial learning loop

Preserve:

`learner spatial action → canonical model transition → visible spatial and semantic evidence → rule-based consequence → meaningful next action`

Require:

- one observable target such as assemble, align, route, balance, place, diagnose, or explain;
- a spatial proposal, measurement, tool choice, manipulation, or decision;
- model state changed by that action, not only camera state;
- visible evidence such as angular error, clearance, contact, flow, route cost, volume, compatibility, or stability;
- a consequence that changes criteria, risk, legal actions, performance, or the next decision;
- deterministic reset and an equivalent non-pointer path.

Do not add success to open spatial exploration. When success exists, derive it from semantic position, orientation, connection, measurement, constraints, or objective—not mesh overlap, animation completion, or a hidden exact transform.

Every spatial consequence must be computed from the current semantic state through declared spatial rules—such as geometry, constraints, tolerances, collision, routing, kinematics, or physics. Canned animation, mesh appearance, overlap alone, or a hidden exact pose may visualize an outcome but must not determine it.

## Write the spatial interaction contract

Refine the first-response construction decision before scene work; no separate written contract:

| Decision | Required answer |
|---|---|
| Learning target | What spatial relation should become predictable, controllable, or explainable? |
| Lost-information test | What essential evidence disappears if flattened? |
| Primary verb | What spatial action changes the model? |
| Entities | Which semantic objects, poses, parts, tools, fields, and regions exist? |
| Constraints | Which axes, surfaces, sockets, collisions, tolerances, capacities, or routes govern action? |
| Evidence | Which scene cues, measurements, criteria, and DOM values change? |
| Consequence | Which next actions, risks, outcomes, or criteria change? |
| Visual world | What subject geometry, material, reference system, lighting, and motion make the rule tangible? |
| Signature mechanism | Which spatial action–consequence event should be remembered? |
| Boundary states | Which initial, active, valid, invalid, failure, success, and reduced-motion states must be authored? |
| Fallback | Which 2D or semantic controls preserve the same decision without WebGL? |

State whether geometry and physics are calibrated, approximate, or explanatory. Name units, tolerances, assumptions, and valid ranges.

## Require a spatial action

Choose a primary spatial verb:

- assemble or disassemble ordered parts;
- align position, direction, plane, or field;
- route through a volume or terrain;
- balance, steer, or control a spatial system;
- place or transform objects under spatial constraints;
- inspect a layer or section, then make a model-relevant decision;
- connect real geographic points, regions, or routes under meaningful constraints.

Write: “The learner changes `<spatial state>` by `<verb>` and reads `<evidence>`.” If the evidence survives unchanged in a flat diagram or the only verb is orbit, redesign the mechanic around a consequential spatial action.

## Compose the learning world

Give the 3D stage the dominant region. Keep primary controls, selected object, measurement, criteria, and feedback adjacent to the scene. The world should be informative before the first action: use a representative nonterminal state, visible targets or reference geometry, and an obvious spatial affordance.

Use the supplied theme direction and shared styling foundations, without treating its classes as mandatory components. Design this page's visual expression from the subject. Derive distinction through:
Keep theme typography and shape/material relationships for equivalent roles; the subject determines geometry and behaviour, not a separate page skin. Physical depth and lighting may serve the real 3D model.

- recognizable functional silhouettes;
- a stable spatial reference such as ground, axes, sockets, section planes, route grid, or terrain;
- material and lighting that clarify contact, depth, layers, and object roles;
- discrete theme roles for category and state;
- continuous theme-derived encoding for continuous error, depth, temperature, density, potential, or risk;
- one signature spatial event tied to the learning rule.

Use scene layers deliberately: environment/reference field, semantic objects, active guides/constraints, effect traces, and DOM evidence. Effects reinforce the exact action; they do not turn a primitive model into a finished world. Avoid transparency stacks when sectioning, clipping, separation, or an exploded state communicates layers more clearly.

## Define semantic spatial state

Keep stable model records separate from meshes:

```js
{
  entities: {
    partA: {
      id: 'partA',
      pose: { position: [0, 0, 0], rotation: [0, 0, 0, 1] },
      constraints: {},
      role: 'movable'
    }
  },
  selection: null,
  operation: null,
  camera: { view: 'overview', azimuth: 0, elevation: 0.5, radius: 7 },
  measurements: {},
  criteria: {},
  phase: 'ready',
  attempt: { actions: [], prediction: null },
  support: { level: 0, type: null }
}
```

Meshes carry `userData.entityId` and render canonical poses. Selection, constraints, measurements, completion, camera, and attempts remain in state. Do not infer semantic truth from mesh color, name, world matrix, collision highlight, or animation progress.

## Separate camera and object control

Avoid ambiguous gestures. Define explicit modes or targets:

- dragging empty background controls the camera;
- dragging a selected handle or object performs the spatial action;
- wheel or pinch changes camera radius only within bounds;
- named view buttons restore decisive viewpoints;
- Escape or a visible Cancel ends the active operation.

Do not allow the camera and object to move from the same gesture. Keep a visible indicator of the current control mode. Important views must be reachable through named buttons, not free orbit alone.

Reset restores the exact canonical camera and target with the model.

## Pick by semantic identity

Convert pointer coordinates through the actual canvas rectangle:

```js
function pointerNdc(event, canvas) {
  const rect = canvas.getBoundingClientRect();
  return new THREE.Vector2(
    ((event.clientX - rect.left) / rect.width) * 2 - 1,
    -((event.clientY - rect.top) / rect.height) * 2 + 1
  );
}
```

Raycast against the smallest intentional target set. Resolve child meshes to the owning semantic entity, then dispatch a selection or operation action. Mirror selectable entities in a DOM list for keyboard access.

Use generous visible handles or semantic groups rather than tiny hidden mesh targets. Hover may preview a target but must not be the only selection path.

## Constrain spatial manipulation

Convert ray hits into a logical proposal on a defined surface or axis:

1. choose drag plane, axis, rotation ring, socket, or volume;
2. calculate the proposed logical pose;
3. apply model clamps, collision, alignment, compatibility, or tolerance;
4. dispatch the constrained pose;
5. derive measurement, criterion, legal actions, and feedback;
6. render mesh pose and DOM evidence.

Do not store an unconstrained mesh drag and validate it only on release. Show guides, target axes, snap regions, clearance, angular error, or collision consequence while the learner acts.

Provide keys, buttons, numeric controls, or select-and-place for rule-relevant precision. A fallback need not imitate free 3D dragging, but it must allow the same model decision.

## Build one Three.js scene

Create renderer, scene, camera, geometry, material, lights, raycaster, and reusable vectors once. Use the host-provided Three.js build and matching APIs. Cap pixel ratio and resize from one observer.

Use render-on-demand for discrete assembly or inspection. Use one clamped loop for continuous steering, physics, or active transitions. Do not allocate geometries, materials, vectors, colors, or listeners inside the frame loop.

Reuse geometry and materials for repeated parts. Use instancing or point buffers when many identical entities are needed, but preserve a stable mapping from instance ID to model entity.

Keep labels, instructions, measurements, criteria, and feedback in semantic DOM. Lighting and materials reveal silhouette, depth, contact, and part roles; they are not a substitute for state evidence.

## Own motion and time

Use motion to preserve object identity, reveal constraint, and connect action to consequence:

- ghost the previous valid pose when comparison matters;
- show axes, guides, clearance, angular error, or route trace during action;
- transition a rejected proposal back to the constrained state without hiding why;
- keep measurements synchronized with the rendered pose;
- hold failure or success states long enough to inspect;
- keep ambient movement slower and quieter than learner-caused motion.

Discrete assembly and placement should render on demand. Continuous steering, physics, or field evolution uses one clamped logical clock; manual Step and autoplay dispatch the same transition. Do not run a physics runner, a Three.js animation loop, and independent tweens that all mutate the model.

Own camera and object timelines. Cancel active transitions before a conflicting action, Reset, or teardown. Under reduced motion, move directly or step between the same semantic poses and camera views; preserve all spatial states, measurements, and consequences.

## Model assembly and layers

For each part, store compact, candidate, and valid target poses or derive them from sockets and constraints. Preserve identity and order through compact, exploded, section, and learner-manipulated states.

- Show compatibility before placement.
- Expose remaining parts, sockets, capacity, or constraints.
- Mark local conflicts and allow removal or correction.
- Gate success from actual position, orientation, connection, and tolerance.
- Avoid one hidden pixel-perfect assembly when several poses satisfy the rule.

## Model geographic interaction

Use a globe only when latitude, longitude, great-circle route, spherical region, or global orientation changes the decision.

- Validate and normalize coordinates.
- Keep stable IDs for places, regions, and routes.
- Define what altitude, width, color, and direction encode.
- Convert selection into a model action—route choice, allocation, comparison, or constraint—not a tooltip only.
- Mirror all choices and evidence in DOM.
- Provide named region views and stop auto-rotation during learner action.
- Prefer a flat map when it preserves the same action and evidence more clearly.

## Preserve a lower-tech path

When WebGL fails or precise spatial input is unavailable, provide named views, entity lists, select-and-place controls, numeric pose controls, or a 2D section that dispatches the same model actions. Preserve the learning loop even if visual richness decreases.

Under reduced motion, make transformations direct or stepwise and stop ambient camera movement. Do not remove spatial states or consequences.

## Make feedback teach

Feedback must identify what changed, which spatial rule produced the change, which evidence supports it, and what action remains possible. Return feedback to the object, guide, route, target, or measurement that produced it.

Wrong or unsafe actions should change inspectable state—collision, blocked connection, excessive error, unstable pose, route cost, depleted capacity, or elevated risk—rather than produce only a detached message. Preserve valid partial assemblies and allow local repair when the model permits it.

When help is requested, escalate from a question about visible spatial evidence, to a contrasting view or analogy, to the governing principle, to a procedural nudge, then to a parallel worked case. Do not reveal the exact pose or route before a genuine attempt unless safety or access requires it.

## Reset and dispose

Cancel active pointer capture, animation frames, tweens, physics, and transitions. Rebuild entities, poses, selection, operation, criteria, measurements, phase, attempt evidence, seed, and camera from the initial factory.

On teardown, remove listeners and observers; dispose owned geometries, materials, textures, render targets, post-processing resources, and renderer state. Track shared assets and dispose them once. A remount must produce one canvas and one input path.

## Diagnose 3D interaction failures

| Failure | Cause | Repair |
|---|---|---|
| Orbit-as-interaction | Camera motion is the only learner action | Add a spatial model verb; otherwise author named views without pretending the camera is the learning action |
| Invisible constraint | Placement fails without spatial evidence | Show axes, sockets, tolerance, clearance, or collision |
| Pixel-perfect assembly | Hidden pose is compared exactly | Evaluate meaningful position and orientation tolerances |
| WebGL lockout | No other route performs the action | Add named selections and equivalent DOM controls |
| Primitive demo | Primitives and orbit controls replace a subject world | Build functional silhouettes, reference geometry, material roles, and a signature mechanism |
| Detached feedback | DOM message and scene evidence disagree | Derive both from one semantic evaluation and place feedback at the spatial cause |

## Verify the 3D interaction

- Prove that the primary action and evidence require spatial state.
- Complete the action through the natural 3D input and the equivalent DOM or keyboard path.
- Exercise selection, cancellation, valid constraint, invalid proposal, boundary tolerance, and local repair.
- Confirm camera, mesh pose, measurements, criteria, legal actions, and feedback derive from one state.
- Inspect the initial state before action and verify visible evidence, spatial affordance, and a meaningful first move.
- Use deterministic named states for overview, active operation, boundary, failure, and success when applicable.
- For continuous models, run the same seed for a fixed step count twice and compare declared outputs.
- Reset during an active operation and compare entities, poses, selection, criteria, seed, and camera twice.
- Resize, force reduced motion and WebGL fallback, then dispose and remount while checking one canvas and stable resource counts.
