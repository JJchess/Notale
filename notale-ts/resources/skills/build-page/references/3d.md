# Authored 3D Scene

Depth, occlusion, assembly, viewpoint, volume, terrain, or geographic coordinates must carry evidence that flattening would lose. Inspection may navigate predetermined evidence, but it must not pretend to change a governing model.

## Write the spatial page contract

Complete:

`The learner should understand <one spatial claim> because <a visible depth, section, assembly, occlusion, or viewpoint relation>.`

Refine the first-response construction decision; no separate written contract:

- audience, page job, and exact spatial relation;
- why a flat representation loses that relation;
- semantic entities and the identities that must persist across views;
- decisive camera, supporting named views, and annotation for each;
- background field, ground/reference system, object material, and one signature spatial event;
- authored object or camera motion and the stable state it produces;
- reduced-motion and non-WebGL evidence;
- performance budget and lifecycle owner.

Give the scene the dominant uninterrupted region. Keep the claim, named-view controls, measurements, and annotations adjacent to it. Resolve palette, typography, surfaces, and controls through the supplied theme; create identity through silhouette, functional geometry, scale, lighting, material response, spatial composition, and motion.

## Require a spatial reason

| Evidence | Suitable form |
|---|---|
| Solid, layered structure, assembly, section, terrain, or volume | Three.js scene |
| Real latitude, longitude, route, or region on Earth | Globe or map; use a globe only when spherical context matters |
| Conventional quantitative relationship | Chart or 2D composition |
| Flat labelled process | SVG or HTML |
| Decorative “future” object or generic network sphere | Do not use 3D |

Write the lost-information test: “If flattened, the reader could no longer see `<specific spatial relationship>`.” If the sentence is weak, use 2D.

## Author the decisive views

Design the initial camera to establish the subject, orientation, and useful starting evidence. Develop the complete explanation through Deck steps using only views that reveal a different relationship:

- Overview for orientation;
- Side or Top for alignment and depth;
- Section for interior structure;
- Exploded for part order and assembly;
- Detail for one labelled spatial feature.

Free orbit is supplemental. It must not be the only route to an important view. Record camera position, target, projection, visible entities, and annotation for each named view. Reset restores the exact initial view.

Compose each named view as a complete still. The initial view must orient the reader, show useful evidence before orbit or playback, and reserve quiet screen-space regions for labels. A section, exploded, or detail view must reveal a different relation rather than merely provide another attractive angle.

## Separate semantic model and meshes

Each meaningful object needs a stable model record:

```js
{
  id: 'layer-shell',
  label: 'Outer shell',
  compact: { position: [0, 0, 0], rotation: [0, 0, 0] },
  exploded: { position: [1.6, 0, 0], rotation: [0, 0, 0] },
  role: 'structure'
}
```

Meshes reference `entityId`; selection, view state, compact or exploded progress, and annotations live in canonical page state. Do not infer meaning later from mesh names, colors, or current transforms.

Preserve part identity through compact, exploded, and section views. Separate parts along a meaningful assembly axis and keep their order and relative scale.

## Initialize one scene

Create renderer, scene, camera, geometry, material, and lights once. Use the host-provided Three.js build and its matching API.

```js
const renderer = new THREE.WebGLRenderer({ canvas, antialias: true, alpha: true });
renderer.setPixelRatio(Math.min(devicePixelRatio || 1, 1.75));
renderer.outputColorSpace = THREE.SRGBColorSpace;

const scene = new THREE.Scene();
const camera = new THREE.PerspectiveCamera(42, 1, 0.1, 200);
camera.position.set(4, 3, 7);
camera.lookAt(0, 0, 0);
```

Prefer render-on-demand for static inspection. Use one animation loop only when a transition or meaningful system motion is active. Never allocate geometries, materials, vectors, colors, or listeners inside the frame loop.

Measure the host, call `renderer.setSize(width, height, false)`, update camera aspect, and update the projection matrix from one resize observer.

## Make objects legible

- Start with restrained ambient or hemisphere fill plus one directional key.
- Use a rim only when it clarifies silhouette or nested layers.
- Enable shadows only when they reveal contact, height, or separation.
- Use semantic color roles and sufficient material contrast between adjacent parts.
- Keep transparent layers sparse; show a section or exploded view when transparency creates ambiguity.
- Reuse geometry and materials for repeated solids; use instancing when repetition is substantial.
- Keep labels, units, controls, and explanations in DOM or accessible SVG overlays.

Model recognizable objects from their functional parts and silhouette rather than exposing collision boxes or generic primitives as the finished explanation.

Use scene layers deliberately:

- background establishes scale, environment, or field without competing with silhouette;
- ground, axes, section planes, or reference geometry make position and depth readable;
- primary objects carry the claim;
- labels, measurements, and view controls remain crisp in DOM or SVG;
- sparse accents mark the current relation or transition.

Use continuous theme-derived encoding for continuous height, depth, temperature, density, or other physical quantity. Use discrete theme roles for parts and states. Avoid transparency stacks; prefer sections, clipping planes, separation, or exploded views when overlapping shells become ambiguous.

## Author spatial motion

Use Deck steps to organize the spatial explanation within the same scene. Change a part, section, alignment, comparison, or camera focus while preserving stable landmarks and part identities; do not introduce a boxed panel for every step. Transfer the sample's authored state sequence to the chassis rather than retaining narration tabs, next buttons, or automatic advancement.

After scene initialization, register `Deck.onStep(renderStep, states.length - 1)`. States 0/1/2 use maxStep 2. The callback restores complete camera, object, and annotation state for any requested step, including backward jumps. Cancel owned tweens before changing step. Genuine free inspection may retain picking or camera controls; those controls must not replace the teaching sequence. Under `?all` and reduced motion, render the complete review state directly.

Motion must reveal a spatial relation or preserve object identity across views. Design named states before interpolation:

- `overview` for orientation;
- `transition` with stable landmarks and one changing relation;
- `decisive` where the claim is visible;
- `settled` for inspection;
- `reduced` with the same evidence and no nonessential travel.

Use one owner for camera and object motion. Do not run independent tweens that fight orbit controls or leave the camera between named views. Disable or suspend manual camera input during an authored transition, then restore it within stated bounds. A host timeline may coordinate DOM labels and scene motion, but the canonical view name, camera target, object state, and annotation remain authoritative.

Ambient rotation is off by default. When environmental motion establishes scale or material, keep it slow, subordinate, pausable, and irrelevant to the only evidence. Render on demand after the scene settles.

## Add bounded inspection

If picking is useful, convert pointer coordinates through the actual canvas bounds and resolve raycast hits through `mesh.userData.entityId`. Dispatch selection into page state, then render highlight and DOM explanation from that state.

Provide a DOM list or named buttons for free inspection when needed, not for sequential teaching beats. Dim context rather than hiding everything outside the selection. Constrain optional orbit radius and elevation; Reset view restores the current teaching step's authored camera.

Picking may reveal authored detail, but it must not silently change the governing model or success conditions.

## Geographic scenes

- Validate finite latitude and longitude, normalizing longitude explicitly.
- State what point size, route direction, altitude, width, and color encode.
- Keep stable IDs and deterministic ordering.
- Aggregate dense points and limit animated arcs.
- Keep selected places and routes in a keyboard-accessible DOM list.
- Stop automatic rotation by default; provide named regions or views.
- Prefer a flat map or table when spherical position does not change the conclusion.

## Provide a useful fallback

The fallback must preserve the relationship, not merely display “WebGL unavailable.” Supply an authored section image, labelled diagram, ordered part list, geographic table, or decisive values. Reduced motion should render the decisive camera state without ambient orbit.

## Dispose owned resources

Cancel animation frames and observers, remove listeners, and traverse the scene to dispose owned geometries, materials, textures, render targets, and post-processing resources. Dispose shared assets once. Dispose the renderer and verify a remount creates one canvas and one listener path.

## Diagnose 3D failures

| Failure | Cause | Repair |
|---|---|---|
| 3D prestige | Depth contributes no information | Flatten the representation |
| Lost camera | Free orbit replaced authored viewpoints | Add named decisive views and exact Reset view |
| Mesh soup | Primitive parts lack semantic identity | Create stable entity records and recognizable functional grouping |
| Transparency fog | Too many layers overlap | Use section, exploded view, clipping, or sparse opacity |
| Generic demo scene | Lighting and orbit exist but no subject-specific world | Rebuild silhouette, reference geometry, material, and decisive view from the claim |

## Verify the scene

- Prove the spatial reason using the rendered initial view.
- Exercise every named view and confirm annotations match visible geometry.
- Use the existing Check step states to confirm actual spatial evidence changes, backward restoration, and a readable final state within one scene, without adding a separate checking loop.
- Inspect overview, decisive, settled, and reduced-motion states as complete still compositions.
- Select one entity through canvas and DOM, when picking exists, and compare state.
- Reset twice and compare camera, selection, transforms, and seeded repeated geometry.
- Inspect draw calls, triangles, and memory after warm-up.
- Resize, force reduced motion, and exercise the non-WebGL fallback.
- Dispose and remount; confirm one canvas and stable owned-resource counts.
- Confirm the non-WebGL fallback preserves the same claim and entity vocabulary.
