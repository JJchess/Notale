**互动讲义可编辑化：调研与建议方案**

调研日期：2026-09-08。范围：当前 `notale-v2` 生成链路、三套实际产物，以及相关项目的官方文档与源码说明。本次交付是方案及有限机制探针，尚未实现完整编辑器；下文成本与架构判断属于工程估算。

2026-09-08 补充：用户已明确采用 TypeScript 建设编辑器后端。具体技术选型、数据库、保存协议、任务执行及部署见 [TypeScript 后端方案](PLAN-editor-backend-ts.md)。本文的编辑能力范围继续有效；后端实现与排期以补充方案为准。

开源复用补充：优先验证 Payload 后端，以及 PPTist/GrapesJS 编辑器底座；Lumi H5P Node.js Library 提供互动课件服务的实际实现参考。下文自建编辑层保留为备选，不应直接视为从零开发决定。详见后端方案第 11 节；原排期属于自建估算，复用路线待原型后重估。

源码研究补充：上述四个项目已实际 clone，另对照 Payload 稳定版。根据源码及 GrapesJS 浏览器探针，下一步优先验证 **GrapesJS＋Notale 互动组件＋Payload 稳定版/PostgreSQL**；真实页面直接导入会丢失脚本，必须做互动适配。研究发现、固定版本及可复现探针见 [开源源码研究报告](experiments/editor-open-source-20260908/README.md)，后端修订见 [后端方案](PLAN-editor-backend-ts.md) 第 12 节。

**1．建议与目标边界**

建议建设 Notale 自己的讲义编辑模式：保留 HTML/SVG/Canvas/WebGL 的呈现能力，增加可持久化的对象模型、对象编辑层和互动组件编辑接口。生成结果成为可再次打开、修改、保存、分享的讲义工程。

默认将“像 .pptx 一样可编辑”理解为：老师能点选改字、替换图片、移动缩放、增删页面、调整顺序、修改讲稿和演示步骤；互动页还可以修改数据、参数和题目，修改后继续运行。实际 `.pptx` 导出作为独立能力评估。

应明确三个层次：普通内容直接操作；互动内容通过配置与专用编辑器修改；任意程序逻辑通过局部 AI 修改及源码入口修改。不能把“有源码”或“整页能拖动”宣称为所有内部对象都能像 PPT 图形一样编辑。如果要求每个 Canvas/3D 内部对象都能直接点选，还需要逐类实现场景编辑器，成本远高于基础编辑功能。

**2．当前项目的证据**

- [core/planner.py](core/planner.py) 使用 `pages/plan/pages.md`、逐页规格及主题输入组织生成；[core/builder.py](core/builder.py) 按标题页、内容页、交互页、代码页分别生成。计划文本表达教学意图，但没有承担最终元素级文档模型。
- [vendor/chassis/CHASSIS.md](vendor/chassis/CHASSIS.md) 已提供默认 1600×900 逻辑画布、缩放、指针坐标和 `Deck.onStep` / `data-deck-step` 分步机制。这能复用为编辑画布与演示运行时的基础。
- [tools/runtime.py](tools/runtime.py) 的 `Write` / `Patch` / `Edit` 修改页面文件，`Check` 检查渲染与交互；这些是生成代理的工具，还不是老师的可视化编辑器。

**3．技术路线比较**

| 路线 | 已有能力与适用点 | 对 Notale 的额外工作 | 判断 |
|---|---|---|---|
| 原页面＋自有对象编辑层 | 保留现有页面和渲染栈；可逐步迁移 | 对象身份、保存、历史、布局和组件协议需要建设 | 开源底座验证后确有缺口时采用 |
| GrapesJS | 页面组件、样式编辑、JSON 工程存储 | 既有脚本、共享变量和 Canvas 内容须适配组件模型 | 保留现有网页布局的优先验证候选 |
| PPTist | 接近 PPT 的选区、图层、页面、主题和元素编辑 | 自由网页布局需转模型；互动节点和代码工作台需扩展 | PPT 式操作的优先验证候选 |
| tldraw | 可考虑为对象画布底座 | 仍需讲义分页、排版及互动适配；有生产许可要求 | 暂不作为默认依赖 |
| H5P 内容类型机制 | 内容数据、编辑字段和运行代码分离 | 不会自动将自由生成页面变为可编辑内容类型 | 借鉴组件协议，不要求整体迁移 |
| HTML → PPTX | 将可映射内容变成 PowerPoint 对象 | CSS、字体和互动存在转换边界；缺少双向同步 | 作为导出分支 |

GrapesJS 官方明确建议使用工程 JSON 保存，HTML/CSS 导出会丢失编辑模型信息；组件脚本在 iframe 中执行，不能直接访问函数外部变量。因此，它能提供编辑基础，但既有讲义依旧需要结构和脚本改造。依据：[工程存储](https://grapesjs.com/docs/modules/Storage.html)、[组件脚本](https://grapesjs.com/docs/modules/Components-js.html)。

PPTist 官方列有页面排序、图层、撤销、文本/图片/图表等编辑与 PPTX 导入导出，同时说明不能保证完全兼容 Office。当前仓库使用 AGPL-3.0，不能默认当作宽松许可组件直接纳入闭源产品；本方案不依赖复制其实现。依据：[PPTist](https://github.com/pipipi-pikachu/PPTist)、[许可证](https://github.com/pipipi-pikachu/PPTist/blob/master/LICENSE)。

tldraw 官方要求生产环境提供适用许可证；没有在本次调研中取得商务报价。依据：[tldraw License](https://tldraw.dev/community/license)。H5P 使用 `semantics.json` 描述可编辑、可验证的数据，另用库清单描述运行依赖，这种分离值得借鉴。依据：[H5P 内容类型开发](https://h5p.org/library-development)。

**4．老师实际怎么编辑**

界面采用左侧页面缩略图、中间讲义、右侧所选对象属性、底部讲稿与步骤。编辑/试运行显式切换，避免拖动图形时误触实验。

| 内容 | 直接提供的编辑体验 | 数据落点 |
|---|---|---|
| 页面与整套讲义 | 增删、复制、排序、隐藏、主题、背景 | deck/page 模型、主题 token |
| 标题、段落、注释、讲稿 | 点选改字、局部格式、颜色、字号 | 富文本数据或具名文案字段 |
| 图片、音视频 | 替换、裁剪、大小、位置、播放配置 | 资源引用及属性；替换图片不代表修改像素内容 |
| 基本图形与结构图 | 移动、缩放、组合、层级、连接线与标签 | 具名形状、分组、连接关系 |
| 公式 | 编辑 LaTeX 并实时预览 | LaTeX 源串，不编辑 KaTeX 输出节点 |
| 数据图表 | 数据表、轴、系列、配色、注释 | 数据集＋图表配置 |
| 实验、模拟、题目 | 初始参数、范围、标签、题干、答案、反馈 | 组件配置及内容字段 |
| 分步与动画 | 调整出现顺序、时长、关键状态，逐步预览 | 步骤及语义状态描述 |
| 代码工作台 | 教师修改题目、起始代码、测试、可视化 | 当前 lesson 文件模型；学生代码另存 |
| 特殊 Canvas/WebGL 内容 | 组件参数编辑；有场景模型的对象可选中；复杂改动选中后交给 AI | 组件源文件、配置、场景描述 |

例如，当前 page-07 可以支持老师把“模型数默认值”从 15 改为 25、换矩阵颜色、改结论模板、移动整个实验区；学生拖滑块时数值仍由模型计算。把多数投票改成加权投票，属于算法修改，进入 AI 局部修改流程，而不是改显示出来的结果数字。

**5．核心架构：工程数据是权威来源**

建议新增 `deck.notale`，作为 ZIP 讲义工程包的候选扩展名；名称可以调整。包内至少有 `manifest.json`、`deck.json`、各页编辑模型、HTML/CSS/JS 或组件模块、数据集、媒体/字体、运行库和缩略图。manifest 记录格式版本、组件版本、文件校验值与资源依赖。

工程数据驱动同一套 Renderer；编辑器在其上添加操作层，播放器运行同一份已保存内容。导出 HTML/PPTX 都从该工程产生。禁止把编辑时的 `document.body.innerHTML` 当作主存档：其中可能包含选框、临时状态、运行时生成图形，并且不包含监听器、闭包和模块依赖。

每个页面、对象、组件实例有稳定 id。数据包括对象类型、父子/分组关系、内容、布局、主题绑定、数据绑定、步骤归属和资源引用。迁移期页面可同时含原始 HTML 源文件与编辑绑定描述；每个字段明确谁拥有它，编辑器将修改写回绑定的数据，而非另存一份与源码相互覆盖的值。后续逐步抽出通用对象，并保留自由 HTML/CSS 自定义模块。

布局至少区分：流式容器（flex/grid，通过顺序、间距、列宽编辑）与自由定位对象（位置、尺寸、旋转）。不能把所有 DOM 子节点都强行绝对定位。老师需要自由摆放某组内容时，可显式转为自由布局；这样做会改变原来的自适应关系，需要即时预览。

拖拽使用逻辑画布坐标，处理 stage 缩放、嵌套坐标和旋转。已有 `Deck.pt` 文档明确不适用于旋转后的元素，不能原封不动套用到支持旋转的编辑器。编辑位置与运行动画使用独立变换层，避免互相覆盖 `transform`；新增包装节点也必须验证 CSS 选择器和布局不变。

页面顺序由稳定 page id 列表维护；文件名只在发布时映射。当前 `Deck.init` 默认按页码跳转，迁移时需改成运行时导航映射，页面复制还要重新生成实例 id、内部引用及 lesson 路径。

**6．互动组件必须有编辑契约**

建议新增独立 `edit-bridge.js` / 组件协议，再通过适配器连接现有 Deck，避免首期大改冻结底盘。以下为拟定接口，并非当前已经存在的 API：

```ts
interface EditableInteraction {
  getConfig(): SerializableConfig;
  updateConfig(next: SerializableConfig): Promise<void>;
  getState(): SerializableState;
  setState(next: SerializableState): Promise<void>;
  setMode(mode: 'edit' | 'play'): void;
  resize(width: number, height: number): void;
  reset(): void;
  dispose(): void;
}
```

组件另外提供配置 schema、可编辑文案、可选对象列表（若支持内部选择）、步骤/静态导出适配及依赖清单。schema 不只声明类型，还应包含参数范围、单位、字段名称和有效性规则。

作者配置、学生运行状态与导出定格状态分开存储。教师改参数默认值，学生操作不覆盖默认值；随机种子可记录，恢复状态能复现结果。Canvas 文案来自配置；动态数值来自模型；图表数据与讲解引用共享同一数据源。简单“替换页面上所有 15”为 25 会破坏这些关系，应通过绑定更新。

第三方/旧版组件无适配器时，允许整体移动与源码/AI 修改，界面明确显示其内部编辑能力。要将其纳入完整可视化编辑范围，必须补适配器或场景模型，不能靠黑盒嵌入验收通过。

iframe 内使用桥接消息同步选区、配置和尺寸；运行内容与编辑器保存权限隔离，校验消息来源和实例身份。导出的内容是可执行程序，这项边界直接关系到项目打开与编辑可靠性。

**7．生成流程如何接入、旧讲义如何迁移**

新生成流程：沿用 planner 的自由教学规划与现有风格系统，在 builder 产物契约中增加稳定对象 id、内容绑定、编辑描述和组件接口；在运行代码初始化前加载作者配置。编辑协议描述对象与可改属性，不预设统一页面模板。

新增编译/校验阶段检查模型与 DOM 的 id 对应、字段写回、未声明可编辑内容、依赖完整性和运行结果。现有 `Check` 继续承担页面质量检查，另加编辑后回归与保存往返检查；只检查截图无法证明可编辑。

旧讲义先在副本导入，保留源文件和资源。自动识别稳定文字、图片、基本 SVG、讲稿和步骤；受脚本控制的内容建立参数绑定，Canvas/WebGL/代码工作台逐类接入适配器。记录每页迁移报告，标明“原生编辑／参数编辑／AI或源码编辑／尚不支持”，不能对整个目录一律标记转换成功。

样本中的运行依赖可能经符号链接共享，代码工作台尤其如此。工程包必须物化实际依赖并重写路径，禁止带着工作区外的 symlink 宣称可搬运。默认输出可由本地服务或 Notale 打开的包；Pyodide/模块加载等情况下不能预设双击 `file://` 就能完整工作。

AI 修改接受选中对象、当前版本和任务范围，优先修改字段/组件源文件；在临时版本生成后，运行视觉与交互校验再提交。用户可预览差异及撤销；版本不一致时不得覆盖老师的新修改。新算法还需要对应数学/行为断言，渲染无报错不足以证明教学内容正确。

**8．建议选用的基础库**

- 元素操作优先验证 Moveable（拖动、缩放、旋转、吸附）与 Selecto（框选）。它们只解决操作手柄/选择，保存、历史和布局仍由 Notale 模型负责。依据：[Moveable](https://github.com/daybrush/moveable)、[Selecto](https://github.com/daybrush/selecto)。
- 富文本优先验证 Tiptap，其 JSON 内容可持久化；只挂在文字对象的编辑表面，避免富文本库接管整页 HTML。依据：[Tiptap Persistence](https://tiptap.dev/docs/editor/core-concepts/persistence)。
- 前端框架沿宿主应用选型；编辑器后端明确采用 TypeScript，推荐 Fastify 模块化单体。现有 Python 生成链路通过隔离任务适配器接入。
- 保存采用 IndexedDB 待提交缓存＋PostgreSQL 不可变版本与版本条件提交，资源使用对象存储，导入导出使用工程包。后台生成、验证和导出由独立 TS Worker 调度。具体协议见 [后端方案](PLAN-editor-backend-ts.md)。

**9．如果还需要真正的 .pptx**

PptxGenJS 可以创建文本、形状、表格、图片、图表等原生演示对象，适合作为结构化模型的导出后端。依据：[PptxGenJS 官方能力](https://gitbrent.github.io/PptxGenJS/)。

另一个值得做对照实验的是 `dom-to-pptx`：项目提供 DOM→PowerPoint 对象映射，以及部分声明式动画转换；其文档明确无限循环、交互触发和非白名单动画不会导出。官方宣传的视觉保真不是在 Notale 上的实测结论。依据：[项目说明](https://github.com/atharva9167j/dom-to-pptx)、[支持边界](https://github.com/atharva9167j/dom-to-pptx/blob/master/SUPPORTED.md)。

| 原内容 | 推荐 PPTX 表示 | 编辑能力与损失 |
|---|---|---|
| 文本、简单形状、表格 | 原生 PPT 对象 | 可编辑；字体与换行需要实测 |
| 常规数据图表 | 原生图表＋数据 | 可改数据；自定义视觉不一定一致 |
| 简单结构 SVG | 可映射时生成形状/连接线 | 才能承诺元素级编辑；SVG 图片插入不等于可拆分编辑 |
| 公式、复杂插画 | 保留源数据，按已验证能力导出矢量/图片 | 首期不能承诺原生公式或路径级编辑 |
| 分步讲解 | 受支持的动画映射，或明确选择拆成步骤页 | 不能自动复刻任意 `Deck.onStep` 程序 |
| Canvas/WebGL 模拟、Python 工作台 | 定格图/视频＋互动版链接 | PPT 内可调整载体，内部实验需在互动版运行 |

每次导出生成逐页兼容性报告，不以整页截图冒充整页可编辑。原生 Notale 工程保留完整编辑能力；PowerPoint 修改后的自动无损回传应视为另一个独立项目。

如果硬要求“PowerPoint 内也能运行网页互动”，Microsoft 提供 Content Add-in 嵌入动态 HTML5 的官方路线，但它需要额外的加载项与部署/宿主适配，不能等同于一个无需配套环境的普通 PPTX。建议只在该目标明确时单独立项。依据：[Microsoft PowerPoint Add-ins](https://learn.microsoft.com/en-us/office/dev/add-ins/powerpoint/powerpoint-add-ins)。

**10．实施顺序、成本与验收**

以下按 1 名前端＋1 名熟悉 TS 后端及生成/运行链路的工程师估算，不是报价；不含未知数量的旧讲义全面修复、实时协作、完整 PPTX 双向转换和所有 3D 场景编辑器。明确 TS 后端范围后，原 8–12 周估算调整为约 9–13 周；阶段可部分重叠，原型后重估。后端主线已包含在其中，见 [后端里程碑](PLAN-editor-backend-ts.md)，不另行叠加。

| 阶段 | 预计历时 | 可审阅交付与通过条件 |
|---|---|---|
| A：风险验证 | 1 周 | 6 页原型：文字、SVG、图像/公式、Canvas 参数实验、分步、代码工作台。实际完成修改→保存→重开→互动；对照一次 GrapesJS 导入成本 |
| B：基础编辑器与保存后端 | 3–4 周 | 页面管理、文字/图片/形状、图层、主题、讲稿、撤销和工程保存；支持流式与自由布局；TS 版本提交、权限与资源存储闭环 |
| C：互动与生成契约 | 3–4 周 | 图表数据、模拟配置、题目/代码、步骤接口；builder 同时生成编辑信息；AI 局部修改可验证并回滚 |
| D：整套交付与迁移 | 2–4 周 | 三套讲义的逐页能力清单、资源打包、完整往返与播放回归；PPTX 如需要则增加导出验证分支 |

PPTX 常规对象导出另估 1–2 周验证/首版工作量，复杂视觉适配随样本重估。不能用该时间承诺任意现有网页完整转成 PPT。

完整验收应包含：

1. 所有目标页面及教学内容均有编辑路径，逐对象记录能力；可视化编辑、参数编辑、AI/源码编辑分别统计，分母来自运行时内容清单，不能只统计已成功导入的节点。
2. 修改标题、换图、拖动和缩放，在关闭重开后保存正确；编辑前未改动对象视觉不漂移。覆盖 1600×900、1280×720 及浏览器缩放场景。
3. 修改图表数据、模拟范围、初始值、标签及题目答案后，数值、图形、反馈保持一致；学生运行状态不污染作者配置。
4. 调整步骤后，前进、回退、`?all` 和末步复看都正确；动画不覆盖老师的布局。
5. 复制/排序/删除页面后，导航、跨页引用和代码 lesson 都正确；复制组件的状态彼此独立。
6. 连续修改、撤销、重做、保存失败恢复、版本冲突行为正确；AI 修改后仍保留可编辑绑定，失败版本不会覆盖当前工程。
7. 工程包换到没有原工作区的环境仍可打开并运行声明支持的能力，无外部 symlink；缺少在线资源的内容明确报告依赖。
8. 使用当前三套 80 页建立迁移验收集合，并补充 3D/音视频案例；当前统计未证明这些额外类型的覆盖，需在原型阶段确认具体文件。
9. 若交付 PPTX：在目标 PowerPoint 版本实际打开并修改文本/图表；核对字体、遮挡、讲稿和步骤，并检查包内原生对象与兼容性报告。仅能解压或截图相似不算通过。

优先立项 A，验证最关键的不确定性：**现有页面在不破坏表现力和互动的前提下，能否稳定建立“修改—保存—重开”的对象绑定。** 该原型是后续全面编辑能力的技术验证，不应被作为整套讲义可编辑化的完成标志。
