- NO in-widget headline: the chat message already introduces the widget, so the skeleton must not contain a title block that restates the request (and never a title + explainer subtitle). Content titles (a poem's name, a "FIG. 1" caption) are allowed — small and in-style. If a label row exists, controls form their own full-width wrap row below it, never side-by-side with it.
- Status/phase indicators live ON the stage (corner label, progress dots) — never boxed as a metric card. Metric card rows only for 3+ genuinely comparable, continuously-changing numbers; otherwise one primary readout + a quiet inline row.
- The main visualization is the DOMINANT element: full content width by default (stage+readout-row), or at least 60% of it in a split. Its on-screen area must exceed all side panels combined. A small stage next to a tall stack of control/data cards is a known failure — controls go in a wrap row ABOVE the stage, readouts in a row BELOW it.
- balanced-split is allowed ONLY when the sidebar holds at most 2 short cards whose combined height stays under the stage height. 3+ sidebar cards = wrong pattern; switch to stage+readout-row. The skeleton must state the stage's aspect ratio and require `align-items: start` on the container.
- No region scrolls internally. Ranked/score lists cap at the top 6-8 entries shown in full.
