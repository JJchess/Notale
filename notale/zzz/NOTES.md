# 这套底盘是怎么来的

来源:`notale/zero` 沙盒里跑的一次实验(内部代号 nn-01)——给 Claude Code
16 个白名单 skill + 一句"神经网络,做得酷炫一些"的指令,不做任何其他引导,
观察它自己怎么做,再把可复用的部分拆出来。所有结论都能在
`lab/llm_calls/nn-01/*.json`(每次 API 调用的完整输入输出)和
`lab/nn-01-chassis.md`(其中一段的可读导出)里查到原始证据,不是推测。

## 1. 底盘的诞生时机——在写任何一页之前

157 次工具调用里,第 7 次就是 `Write(deck.css)`,第 9 次是 `Write(deck.js)`,
而第一页 `page-01.html` 到第 11 次才开始写。它先花 4 次工具调用扫描所有
skill 描述、调用一次 `frontend-design`,拿到方案立刻把整套设计 token +
四种版式模板 + 组件库一次性定死,之后 150 次调用里**再没改过组件种类**。

**含义**:多样性的窗口只存在于"造底盘"这一步。这也是 `base.css` 拆出来
之后必须配一份 `theme.contract.md` 的原因——不把这一步的要求写清楚,
harness 每次跑出来的底盘都会收敛到差不多的几种形态。

## 2. 指针坐标换算不是它自己想到的花活,是架构必然

`base.js` 里的 `Deck.pt()` 解决的问题:舞台被 `transform:scale()` 整体
缩放后,屏幕上的鼠标坐标和 1600×900 逻辑坐标系不是同一套数字,直接拿屏幕
坐标去判断"点没点中"必然出错,而且窗口越不是标准 16:9 比例,偏差越大。

这次生成独立写出了几乎一样的解法(第 19 次调用,看完第一次截图之后修的)。
`slide-sim` 这个 skill(这次实验里排除掉、它没读过)把同一个坑列为
"最大的坑"。两个独立信源认定同一个坑,说明这是"固定画布+整体缩放"这套
架构下的结构性必然,不是巧合——**任何复用这套架构的页面都要处理它**,
所以进了冻结层,不必每次重新发现。

## 3. canvas 拉伸修复也是同样性质,而且有它自己写的诊断证据

`.cv-fill{ width:100%; height:100%; }` 这条修复,起因是它自己写了一段
探测脚本量出 canvas 默认渲染尺寸只有 300×150(浏览器对 `<canvas>`
这类替换元素的既有行为,`inset:0` 单独作用不生效)。它的原始注释是:
"canvas 是替换元素,inset:0 拉不开,必须显式给宽高"——这条注释本身就是
诊断结论,置信度最高的一条发现。

## 4. "先出方案再批评"这一步,观测不到——它被指示藏进了 thinking

`frontend-design` skill 原文里有一句直接指示:

> Try to do a lot of this planning and iteration in your thinking, and only
> show ideas to the user when you have higher confidence it'll delight them.

对应实测:调用 `frontend-design` 之后那次思考用了 10,273 token(全程前
14 次调用里的峰值),但展示出来的文字只有一句"现在开始搭底盘"。下一次
调用思考量骤降到 10 token,直接把 11,810 字符的 `deck.css` 一次性写出来。

**这次会话还带着 `redact-thinking` beta,思考正文被服务端抹掉,只剩
token 数**——所以"方案是否真的做了自我批评、有没有真的避开三种 AI 通用
脸"这件事,连事后翻记录都验证不了。

**对 harness 的直接含义**:如果只是把"先出方案再批评"这句话塞进一条
prompt,指望模型自己在心里想清楚,你拿不到任何审计信号——好与不好全凭
运气。`theme.contract.md` 里把这一步要求成"必须以可见文字产出方案"，
就是为了把这一步从"黑箱赌一把"变成"你能读、能拦截"。

## 5. 截图会话自检是 skill 指示的,不是模型自发

同样在 `frontend-design` 正文里:

> Critique your own work as you build, taking screenshots if your environment
> supports it – a picture is worth 1000 tokens.

这次生成的"写页面→playwright 截图→读图→回改"闭环,直接对应这句指示。
如果 harness 里没有这类"渲染后看一眼再决定要不要改"的阶段,这不是模型
能力问题,是没人告诉它可以/应该这么做。

## 6. 全量重发架构下,截图会一直累积,从不清理

这次会话用的是"每次调用重发全部历史"的架构(Anthropic Messages API 本身
无状态)。第 19 次调用出现的第一张截图,到最后一次(第 159 次)调用依然
原样带着,前后被重复处理了 140 次。到会话结束时,同时挂着 39 张完整截图,
仅这部分就占了约 7.5 万 token 的输入。

**对 harness 的含义**:如果每页构建也走"截图自检"这个闭环,截图只在
"当前正在处理的这一页"这次调用里有用,不需要带到下一页的调用里——用完
就该从后续输入里拿掉,不要学这次全量保留的做法。

## 7. Prompt 缓存:把 base.css/base.js 放在提示词最前面,加缓存断点

同一份实测里能看到:第一次调用把约 6.7 万 token 写入缓存
(`cache_creation=67,453`),后续调用大部分直接读缓存
(`cache_read` 六万多,真正全新处理的部分常年是 `input=2`)。

`base.css` + `base.js` 加起来大约 6K token,如果 harness 里每一页都是
独立调用,把这两份内容放在提示词最前面、加上缓存断点(Anthropic 是
`cache_control:{"type":"ephemeral"}`,OpenRouter 因供应商而异,见前面
的调查记录),第 2 页起基本上只按十分之一价格重新读这部分。断点前面的
内容必须逐字节不变——时间戳、随机 ID 这类东西绝不能混进去,否则缓存
静默失效,不报错,只是每次都重新付全价。

# 第二轮(nn-03)的发现

同一个 query「神经网络」,14 页。相对 nn-01 同时改了六样:46 条重写描述、+33 个新 skill、
库预置到零成本、要求写出每页的形式选择与否决理由、并行 subagent、找图与文生图能力。

## 8. Skill 白名单没有被使用过一次

主线程 0 次,14 个 subagent 也是 0 次。**不是没看到** —— 抓包证实第 3 次调用注入了完整清单
(59 个 skill,用的正是审查员读完正文后重写的描述)。看到了,没调。

但库用上了:`anime.min.js` ×2、`d3.min.js` ×1。也就是说它需要那个能力、找到了对应的库、
直接用了 —— 完全绕过了 `animejs` 和 `d3-viz` 这两个 skill。

配合另一个独立测量(盲检索测试:原始库侧描述 18/18,手写问题侧 18/18,审查员重写 18/18,
三版无差别),结论是:

**描述质量不影响 skill 是否被调用。模型已经会用这些库,读一份文档换不来任何东西。**

skill 想被调用,内容必须是它不知道的东西 —— 具体的坑、验证过的实现约束 —— 而不是
"某个流行库的用法综述"。

## 9. 形式多样性确实提高了,但功劳不在 skill

| | nn-01 | nn-03 |
|---|---|---|
| skill 调用 | 1 | **0** |
| 用到的库 | 0 | **2** |
| 形式种类 | 2 | **5** |
| 单页体积 | 9.7–15 KB | 20.6–29.9 KB |

把库预置成零成本(文件已放好、版本写明、一行引用)起作用了;把描述改好没起作用。

## 10. 并行是真的,但救不了总时长

主线程在**一条消息里发出了全部 14 个 Agent**,而且 subagent 在这条消息还在流式输出时
就陆续开跑了(最早的 subagent 完成于 16.8 分钟,而那条主消息 23.2 分钟才输出完)。

注意:Claude Code 的 jsonl 会把一条 assistant 消息拆成多行,**用 jsonl 判断"是不是同一条
消息发出的"会误判成串行**,必须用代理抓到的原始请求体来判断。

但并行救不了总时长,因为瓶颈是尾部延迟:

```
构建阶段墙钟 56.4 分钟
  最快单页   3.9 分钟
  中位数    13.4 分钟
  最慢两页  55.2 / 57.0 分钟   ← 其余 12 页早就跑完在等这两个
```

即使 14 个严格同时启动,构建阶段仍是 57 分钟,只省 2.9 分钟。
**该做的不是并行,是给单页构建加超时和降级。**

## 11. 规划阶段的浪费是可以预置掉的(已落实)

首次派发 subagent 之前 13 次主线程调用,其中确定属于浪费的:

- `pwd && ls -la && ls pages/ && ls pages/assets/lib/` —— 探环境
- `head -c 300` 六个库文件 —— 靠文件头猜版本
- **连续三次 grep `three.min.js` 的 REVISION,第一次直接返回空** —— 压缩构建里抓不到

它要版本号是正当的(three r152 把 `outputEncoding` 改成了 `outputColorSpace`,写错就崩)。
不给版本号,它只能去猜。

已落实的修复:`pages/assets/lib/LIBS.md` 现在写明**精确版本号**和 API 世代提示,
指令里也点明"不需要检查、不要去文件里查版本、`pages/` 下除了 `assets/lib/` 是空的"。

**通用原则:凡是 harness 自己知道的事实,都要直接告诉它,不要让它现场勘察。**
它每一次勘察都是一次调用、一次等待,而且可能失败(这次三次里第一次就失败了)。

## 12. 观测工具必须对被测对象无害

这轮代理崩了 4 次(685 次调用中的 0.6%),原因是我自己的 bug:解析被截断的流时,
`except` 分支里对已经 pop 过的键再 pop 一次,抛 KeyError 逃出 handler。

后果不只是丢数据 —— **每次崩溃都断开连接、触发客户端重试,把总时长拖长了**。
所以那轮报出来的 79.6 分钟是被工具污染过的数字。

修复是两层:解析层兜底(截断内容存进 `_unparsed`),记录层整体 try(任何记录失败只打日志)。

**这条对 harness 同样适用**:pipeline 里加的日志、校验、截图,任何一环失败都不该让主流程
重试或中断,否则你测到的性能数据里混着你自己制造的开销。

## 13. 底盘的收录标准:「换主题也不会想改」,不是「上一次写过」

`base.css`/`base.js` 第一版是直接从 nn-01 的 `deck.css`/`deck.js` 拆的,
拆的是「机制 vs 内容」。这个切法不够 —— 它把一大堆**审美**当成机制留下了:
全大写、`.28em` 字距、2px 圆角、9.5–13px 的小字、452px 的固定窄栏、
一整套顶栏/导航轨道/面板/按钮。

nn-03 的选择器比对说明了后果:

```
base.css        93 个选择器
nn-03 deck.css  100 个 → 与 base 重合 20,独有 80
nn-01 deck.css   97 个 → 与 base 重合 89,独有  8
```

和来源那轮重合 89,和下一轮只重合 20。**冻在底盘里的那套组件,下一个主题
既用不上、又要绕开**,是负资产;而且它里面还藏着两处写死的
`rgba(255,255,255,…)`,等于偷偷假设了深色背景。

正确的收录标准是「**换任何主题都不会想改的东西**」。按这条重新过一遍,
base.css 从 93 个选择器降到 15 个,组件全部移进 `examples/`(只作参考,
留的是「一套组件要覆盖哪些角色」这份清单,不是那些数值)。

## 14. 底盘真正的价值不是省时间,是防无声退化

同一份比对里还有一个更要紧的发现。nn-03 独立重新推导出了四条已经在
base 里冻着的机制(固定画布缩放、`:focus-visible`、`getBoundingClientRect`
指针换算、devicePixelRatio 适配),但**漏了两条 nn-01 有过的**:

- `canvas` 显式宽高(替换元素拉伸修复)
- `prefers-reduced-motion` 降级

漏第二条意味着 14 页满是动画的内容对前庭敏感的读者不友好,而且**没有任何
报错**。所以底盘省下的那几分钟不是重点 —— 重点是它把「上一轮已经解决的
机制」变成不会再丢的地板。

推论:底盘只该冻**会被无声漏掉、且漏了有实际代价**的东西。审美不属于这一类
(漏了一眼就看得出来),机制和可访问性属于。

## 15. 缩放架构下,canvas 的采样率不能只看 devicePixelRatio

原来的 `fit()` 用 `min(dpr, 2)`。但舞台整体 `scale(--s)` 过,一个 800 逻辑 px
宽的 canvas 最终占屏 `800·s·dpr` 个物理像素。在 2560×1440 这类大屏上 `s=1.6`,
只按 dpr 算就是 1,画布被放大 1.6 倍显示 —— 发虚,而且这种虚在开发者常用的
笔记本上(`s<1`,反而是超采样)根本看不出来。

现在按 `clamp(dpr·s, 1, 2)` 算。实测四种组合:

```
1366×768  dpr1  s=0.85 → ratio 1.0
2560×1440 dpr1  s=1.60 → ratio 1.6     ← 旧代码这里是 1.0,发虚
1440×900  dpr2  s=0.90 → ratio 1.8
reduced-motion 下 Deck.loop 只跑 1 帧(画静态终态,不是空白)
```

同类的一条:`Deck.pt()` 在 `touchend` 上要读 `changedTouches` —— 那时
`e.touches` 是空的,只读 `touches` 会拿到 `undefined` 然后整个交互在手指
抬起的瞬间失效。

## 16. 并行构建的墙钟,一半以上花在「写任务简报」和「一个慢子代理」上

nn-03 的 14 个 subagent 确实是**一条消息发出去的**(14 个 Agent 调用共享同一个
`requestId`/`msg_id`,查过了)。但一条消息 ≠ 同时起跑:tool_use 块是随流式输出
逐个被派发的,所以第 1 个和第 14 个之间差了 **6:24**。31,639 字符的简报按 82
字符/秒吐出来,末尾那个 subagent 就是白等了六分半。

```
构建墙钟 41:22   串行需 187:03   加速比 4.5×   峰值并发 13
41:22 = 起跑铺开 6:24 + 末个 subagent 自己跑 34:58
最慢 37:17(page-09) / 中位 13:14 / 最快 3:52
```

两处成本都不在「模型写得慢」上:

1. **简报的串行代价 6:24**。简报是主 agent 一个字一个字写出来的,N 越大越贵,
   而且完全线性。程序化拼装(模板 + 每页少量差异)能把这段压到接近 0。
2. **长尾**。墙钟由最慢的那一个决定,中位数只有它的三分之一。page-09 花 37 分钟
   不是卡住了,是在做数值参数搜索(详见 #27 —— 我一开始把它记成「搭脚手架」,
   查错了)。

时间构成:API 往返 95%,工具执行 5%。**产出 token 里 51% 是 thinking** —— 真正
的大头是思考,不是打字。

并发本身**没有**把单次生成拖慢,查过了:

```
并发 1-3    144 次   75.0 tok/s
并发 4-7    114 次   75.8 tok/s
并发 8-10    85 次   79.1 tok/s
并发 11+    103 次   79.8 tok/s
```

所以「多开几个 subagent」不吃亏,加速比的天花板在长尾(和简报的串行代价),
不在带宽。要压墙钟,该做的是压简报生成、给单页设时间预算,而不是少开几个。

## 17. 三个会让时间审计得出相反结论的读数陷阱

都踩过,记下来:

- **`usage` 只有响应组的最后一行是完整的**。前面的 thinking/text 行带的是占位值
  (`output_tokens: 2`)。按第一行读,一次 622 秒吐 52,108 token 的正常生成会被
  算成 0.003 tok/s,于是「55% 的 API 时间疑似卡住」—— 全是假的。改成取组内最大值后,
  真实停顿只有 2%,整体 78 tok/s。
- **主 jsonl 里 Agent 的 `tool_result` 行,时间戳写的是派发时刻**(实测只差几毫秒),
  不是完成时刻。拿它当结束时间,每个 subagent 的时长都是 0:00。完成时刻只能取
  subagent 自己那份 jsonl 的最后一行。
- **subagent 交付后会话不关**。协调者事后发来的返修消息记在同一个文件里,于是
  「最后一行 − 第一行」把「交付完干等 review」也算进构建时长。nn-03 里 page-05
  的 57 分钟其实是 9:56 构建 + 34:55 空转 + 12:08 返修。不切段就会把两个正常的
  subagent 当成异常来查。

另外 proxy 记到 623 次 subagent 请求,trajectory 里只有 432 轮 —— 差的 191 次全是
`end_turn` 的十几 token 短回复(「正在改 page-10 的 CSS」这类状态行),不是重试。
拿 proxy 的调用总数当推理轮数,每轮成本会算低三成。

## 18. skill 能防的错,和编辑循环在修的错,几乎不相交

把 nn-03 的 134 次页面编辑逐条读完、归类,再回头查 49 个 skill 的语料:

| 类别 | 条数 | 占比 | 现有 skill |
|---|---|---|---|
| 版式挤压:内容塞不进固定画布 | 33 | 25% | ✗ 只有 3 个 skill 顺带提 overflow |
| canvas 文字/坐标/遮挡手工调 | 33 | 25% | ✗ textBaseline 0 个、measureText 0 个 |
| 领域算法与数值正确性 | 20 | 15% | — 讲义内容本身 |
| 对比度/可辨识度 | 12 | 9% | ✓ 12 个 skill 讲 contrast |
| 死代码清理 | 11 | 8% | — |
| 跨页一致性 | 8 | 6% | — 协调成本 |
| canvas 尺寸与容器对不上 | 6 | 4% | ✗ |
| 动画帧率/时序 | 6 | 4% | ◐ delta time 3 个 skill |
| 事件监听/状态 | 5 | 4% | ✓ 20 个 skill 讲 cleanup |

**✓ 13% ◐ 4% ✗ 54% — 29%**

决定性的一个数:134 次编辑里,涉及 `prefers-reduced-motion` / `focus-visible` /
`aria-` / `tabindex` / `touch-action` 的是 **0 次**。

原因很直白:编辑循环修的是**看得见的错**(文字压住了、方块顶出面板了、canvas 比容器
宽 2px),而 skill 覆盖得最好的那些是**看不见的错** —— 页面看起来完全正常,没有任何
东西会促使它去改。

推论:装上 skill **不会缩短编辑循环,一秒都不会**。它补的是另一个集合。这和 #14 对
底盘的结论是同一条,只是覆盖面不同:skill 管质量地板,底盘管结构性坑,渲染自检管
canvas 手工排版 —— 而且渲染自检**增加**编辑数(自检 8 次的页面改了 26 处,自检 0 次
的改了 0 处),因为它真的看见了。

## 19. 「页面里没有」不等于「这一轮没有」—— 这个坑第三次踩了

我先按只 grep 页面的结果下过结论:「focus-visible 0/14,模型永远不会发现」。**错的。**
`focus-visible` 在 nn-03 自写的 `deck.css` 里,一直都在。同样地 `getBoundingClientRect`、
`devicePixelRatio` 都住在 `deck.js` 里。页面级 grep 一律报 0,看着像全线失守。

## 25. 改法:卡字号(出口),放开页数(出路),两条必须配套

**排期:最终决定一次上齐,进 nn-04。** 一度押到 nn-05,理由是变量太多归因会混;
后来改主意,原话是「不要押后了,一起上吧」。取舍是明知的:归因会比分批粗,
但各变量的观测指标基本不重叠(密度看 check_density、底盘看 check_page 的
canvas-* 闸、骨架看 page-id、自检看调用次数、隔离看越界报告),真正混在一起的
只有「页面整体好不好」这种本来就没有单一指标的判断。
对照基线用 nn-03 —— 它这四条一条都没有:字号不达标 66%、中位 12.5px。

两条硬约束,都不说「该怎么做」:

- **字号地板**。按物理下限倒推:刻度/单位 ≥12px、标签/图注 ≥14px、正文/说明句 ≥16px,
  折行的多行文本行高 ≥1.35 倍。堵死「缩小」这条最省事的退路,但不规定怎么解决 ——
  删内容、拆页、改成分步显示都行。
- **页数不设上下限,不要先定页数再往里填**。nn-03 的「14 页」出现在它的**第一句话**里,
  比 PLAN.md 早 650 秒:「保证 14 页是"一套"而不是"14 张"」—— 规划还不存在,页数已经定了。
  而当时指令原话是「N 由你根据 query 自己决定」,等于邀请它从 query 直接拍一个数。

两条必须配套:只卡字号而不放开页数,它没有出路,只会去压行高、压间距;只放开页数
而不卡字号,它没有动机拆页。

`lab/check_density.py` 负责测。分档不靠作者声明靠**文本自身的样子**(只有数字符号的
是刻度、带句读或够长的是说明句、其余是标签)—— 声明式分档会被绕过,把什么都标成
"刻度";文本本身不会。对 nn-03 跑出来 **437/667(66%)不达标**。

行高不能设全局下限:实测中位 1.20、82% 低于 1.35,但里面大量是按钮和 chip 这类
**单行**标签,对单行文字要求行高没有意义。只对渲染高度够两行的元素要求。

已知盲区:canvas 里 `ctx.fillText` 的字不在 DOM 里量不到。粗查内联脚本的 `ctx.font`
发现更糟 —— page-14 是 9px,page-11 是 9–11px。这部分只报不判。

## 28. 实时训练不该上 ML 库 —— 要的是逐帧控制权,而库的 train() 是黑箱

调研过 brain.js / TensorFlow.js。结论是**不往 lib/ 加 ML 库**:

- 「在页面上实时训练并可视化」需要的是「这一帧推进 12 个 mini-batch,然后我来画」
  这种控制权。brain.js 的 `net.train()` 是阻塞黑箱;tfjs 能做(`onBatchEnd` +
  `await tf.nextFrame()` 让出渲染帧),但那是把一套 async/promise 控制流叠在自己的
  rAF 循环上,而且要拖进约 1MB。
- nn-03 的 page-11 手写了一个两层 MLP,`for(i=0;i<STEPS_FRAME;i++) step()` 塞在 rAF
  里,同步、可随时读权重,实测 4 秒收敛到 99.4%。**对 200 个点的两层网络,手写就是
  更合适的解**,库在这里是负担。

skill 库里也没有:`tensorflow|neural network|machine learning` 命中 **0 个**。

所以「每个交互背后有真实算法执行」这个能力,靠的不是库,是:
(a) 设计期能快速验证(numpy / node,已具备,只是要告诉它);
(b) 运行时保持逐帧控制(手写,不要库)。

真要加库,该加的也不是 ML 而是**求解器**(page-09 那类参数搜索)。scipy 这台机器上
没有;fmin 最新版停在 0.0.4 早已无人维护。numpy 已经覆盖了绝大部分,先不加。

## 30. tfjs 实测:可视化没问题,但小网络实时训练慢两个数量级

上一条(#28)我是靠推理下的结论。补做了实测,推翻一半、坐实一半。

**基准第一版是错的**,我拿 `[8,8]`+relu+batch32 对比,而 page-11 真实配置是
`[10,10]`+tanh+batch16+每帧 12 步,而且 **`HEAT_FRAMES=8` —— 热力场每 8 帧才重算**。
漏掉最后一条等于把 tfjs 的热力场成本放大了 8 倍。逐项对齐后重测(240 帧):

```
                  tfjs 4.22    手写
准确率            0.905–0.965   0.975
每帧              102.7 ms      0.79 ms
其中训练          87.2 ms       0.24 ms
热力场一次(80×80) 124 ms        4.4 ms
决策边界平均绝对差            0.026–0.039
```

**可视化完全没问题**:同一份数据画出的决策边界肉眼分不出;每层激活也拿得到
(`tf.model({inputs, outputs: layers.map(l => l.output)})`,0.1ms/次)。

**但慢 130×**。换成 tfjs 惯用写法(一次 `fit` 内部跑完所有 batch,而不是 12 次
`trainOnBatch`)从 190ms 降到 102ms,仍然不可用。

注意前提:测试机没有真显卡,跑的是 swiftshader 软件 GL。但慢的成因不是算力 ——
2→10→10→1 配 6400 个网格点,浮点量微不足道,时间全花在每帧上百次 kernel launch
和 `dataSync()` 的 GPU→CPU 回读上。真显卡砍掉的是本来就可忽略的那部分。

**决定性的数是代码占比**:14 页 7,289 行内联 JS 里,算法相关只有 149 行(2.0%)。
canvas 绘制才是 1,386 行(19%),其中文字定位与度量 298 行(4.1%)。tfjs 在最重的
page-11 上省 25 行 / 697 行 = 3.6%。**库能覆盖的面本来就很小。**

结论:`tf.min.js` 还是放进 `lib/` 了,但 LIBS.md 里写明边界 —— 小网络实时训练
不要用它(附实测数字和"手写四十行"的做法),该用它的是**加载预训练模型、真图片
上跑卷积、大到 GPU 才算得动的矩阵**,那些手写做不到。外加 `tf.tidy` 不写就漏张量
这个坑(实测 60 帧 `numTensors` 从 0 涨到 310 且不回落)。

真正的杠杆不在 ML 库,在 canvas 绘制那 19% —— 而且文字定位那 4.1% 正好也是编辑
循环最大的一块(C 类 33 次编辑,占全部编辑的 25%)。

## 31. 把 page-11 的手写网络打包成 zzz/lib/mlp.js

那 106 行(按函数边界实数,占 page-11 内联 JS 的 15.2%)质量确实高,几处不是随手写的:

- `sigmoid` 按 z 正负分支,大负数时不会 `exp` 溢出
- ReLU 用 He、tanh/sigmoid 用 Xavier,分开初始化
- 交叉熵把概率裁到 `[1e-7, 1-1e-7]`,否则一个 `log(0)` 毁掉整条损失曲线
- 激活导数同时吃 `z` 和 `a`,tanh 用 `1−a²`、sigmoid 用 `a(1−a)`,不重算前向
- 每层激活留在 `layer.a` 上,可视化直接读,不必再跑一遍前向

剥掉的页面耦合:`S.hidden/S.act/S.lr` 那套全局、`shuffle`/`diverge` 外部函数、
**输入维度写死为 2**。补上的:任意输入维度、可选种子(教学页需要「重来一次还是
这样」)、`reset()`、`field()` 批量求决策边界、`activationLevels()`。

浏览器 `file://` 下实测:`[2,10,10,1]` tanh lr0.3,240 帧每帧 12 个 mini-batch,
**准确率 0.995,每帧 0.66ms**,和 page-11 一致。

### 打包时发现原实现一个真问题

原来的 `applyGrads` 用 `isFinite` 判发散。**抓不到。** 实测 lr=800 跑 300 步:

```
|w|max = 4,964,024      准确率 0.500      损失 8.06      isFinite 全程为真
```

原因:sigmoid 输出饱和到 0/1 之后 `(a−t)` 的上界就是 1,梯度永远变不成 Inf,
权重能一路涨到百万级而始终有限。page-11 另有一套损失判据
(`loss > minLoss*1.7 + 0.10 && loss > 0.55`),但那条只能抓「先正常后崩」,
抓不到「一开始就崩」—— 实测同样 lr=800 它一次都没报警。

现在加了权重幅值闸(`cfg.wmax`,默认 1e4):

```
lr=0.3   |w|max   4.3   未触发   acc 0.960
lr=3     |w|max  10.3   未触发   acc 0.805
lr=30    |w|max  54.9   未触发   acc 0.500   ← 没学会,但数值没崩
lr=800   |w|max 14056   第 1 步触发
```

## 34. 换题目:两轮下来 15 个库只用过 2 个,不全是模型的问题

## 35. 「subagent 看不到彼此写出的内容」是假的 —— 文件系统是通的

指令原话写着「这些 subagent 各自处在独立上下文里,**看不到彼此写出的内容**」。
上下文确实隔离,但**文件系统不隔离**。实测 nn-03:

```
6/14 个 subagent 越界读了别人的页面,共 10 次
其中 8 次的目标是 page-01 —— 第一个建好的那页被当成了样板
page-03 还读了正在被并发写入的 page-04 和 page-05
```

两层问题,后一层更要紧:

1. **竞态**。14 个 agent 并发写,读到的可能是半成品。
2. **它绕开了实验要问的那个问题。** 这个实验问的是「N 个隔离上下文靠什么合成
   一套连贯的东西」,而答案有一部分是「互相照抄第一页」。那协调者的契约设计
   到底起了多少作用,就测不出来了 —— 也解释了为什么 nn-03 的页面看起来挺一致。

已改:指令里那句改成「看不到彼此的**对话**」(这才是事实),并新增一条硬约束
「只读写自己那一页的 HTML,不许读别的页面文件」,同时明确共享 CSS/JS、契约、
规划文档照读 —— 限制只针对别人的 `page-*.html`。

光写进指令拦不住(文件系统还是通的),所以 `audit.py` 加了 `audit_isolation()`:
按 subagent 的 meta 认出「自己那一页」,再扫它所有工具调用里出现过的
`page-NN.html`,报越界次数和目标。nn-03 的 6/14、10 次就是基线。

**一般化的一条**:凡是指令里断言的隔离,都要问一句「靠什么保证」。上下文隔离是
运行时给的,文件隔离没人给 —— 断言了但没有机制兜底的约束,等于没有。

## 37. nn-04 一次上齐:变了六样,以及为什么还敢归因

原计划分两轮,最后决定一次上齐。相对 nn-03 变了六样:

```
换题目          神经网络 → 火箭与轨道,并写明撑一堂 90 分钟的课
三个预置件      base.css/base.js 底盘、new-pages.py 骨架、selfcheck.py 自检
四条内容约束    字号地板、页数放开、交互为理解服务、点名小游戏/三维
跨页隔离        只读写自己那一页的 HTML
skill 描述压缩  28,215 → 8,115 字符(检索率压前压后都 18/18)
```

**归因确实比分批粗,这是明知的取舍。** 之所以还敢做,是因为这几轮把观测指标都做成了
互不重叠的:

```
底盘     → check_page 的 canvas-dup / canvas-dpr / motion-* 闸
骨架     → page-id / page-total 闸,new-pages.py 调用次数
自检     → selfcheck.py 调用次数
四条约束 → check_density 不达标率、页数、库使用量、形式种类
跨页隔离 → audit 的越界报告
描述压缩 → 清单里还有没有裸名字
```

真正混在一起的只有「页面整体好不好」——那本来也没有单一指标。

**这件事本身值得记**:能承受「一次上齐」的前提,是先把每个变量的专属指标做出来。
指标先行,才谈得上敢不敢并轨;没有指标的时候只能一次动一个变量,慢但没别的办法。

对照基线一律是 nn-03(四条约束一条没有):字号不达标 437/667=66%、中位 12.5px;
15 个库只用 2 个;跨页越界 6/14、10 次;清单裸名字 10 条。
