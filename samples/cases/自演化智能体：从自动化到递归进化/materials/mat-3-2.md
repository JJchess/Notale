## 代码生成作为自我改进的载体

上一节我们给出了 RSI 的形式化定义：$f_{t+1} = \mathcal{I}(f_t, D_t)$。这个公式很优雅，但它留下了一个关键的空缺——改进方案 $c_t$ 究竟以什么形式表达，又是如何被应用到智能体身上的？

答案几乎是不言自明的：代码。

### 为什么代码是 RSI 的天然介质

在人类文明的历史上，每当需要记录、传递和执行可复用流程时，我们发明了多种媒介——口头指令、文字手册、流程图、数学公式。但在所有媒介中，只有代码同时具备三个对 RSI 至关重要的性质：

**可执行性**（Executability）：代码可以不加解释地被机器执行。改进方案一旦以代码形式表达，就不再依赖"理解"——它可以直接运行，产生客观的反馈信号。这使得评估不再是主观判断，而是基于编译器/解释器的客观结果。

**可验证性**（Verifiability）：代码的正确性可以通过测试来验证。单元测试、集成测试、类型检查等形式化工具可以在数秒内给出二元的通过/失败判断。这是任何自然语言描述的改进方案都无法提供的效率。

**可组合性**（Composability）：代码是模块化的。一个改进可以被限定在某个特定函数或模块内，不影响系统的其他部分。这种隔离性大大降低了自我改进的风险——一个失败的改进通常只影响局部，而不会导致全局崩溃。

这三个性质共同构成了一个强大的反馈回路：生成代码 $\to$ 执行代码 $\to$ 获取结果 $\to$ 根据结果修正代码。这个回路的周转时间可以短至秒级，使得在极短的时间内完成数十轮改进成为可能。

### 代码生成改进的三种层级

在使用代码作为自我改进的载体时，我们需要区分三个层级的改进对象：

**层级一：改进输出代码**。智能体被要求完成一个编码任务（如"写一个排序函数"），如果结果不正确，智能体读取错误信息并修正自己产出的代码。这是最浅层的改进——智能体的自身架构没有任何变化，只有其产出被迭代优化。这是第二章"反思循环"的直接应用。

**层级二：改进工具代码**。智能体维护一组可复用的工具函数和库，这些工具被用于解决未来的任务。当一个工具函数在处理新任务时表现不佳，智能体可以修改该工具的实现，使它在后续任务中更有效。这种改进是跨任务的——它不是为单个输出服务，而是为智能体的"工具箱"服务。

**层级三：改进智能体代码**。智能体修改的是定义其自身行为逻辑的代码——包括提示词模板、策略选择逻辑、工具调用编排、甚至评估标准本身。这是真正的 RSI 层级，与"输出精炼"有了本质区别。

这三个层级并非互斥，而是一个能力递进的光谱。一个成熟的 RSI 系统通常同时进行三个层级的改进，但只有层级三触及了递归自我改进的理论核心。

### Self-Debugging：让代码学会调试自己

2023 年，Chen 等人提出的 Self-Debugging 方法是代码生成领域的一个重要里程碑。该工作的核心洞察是：不同于人类程序员需要手动解读错误信息，LLM 天然具备理解报错信息并用自然语言解释错误原因的能力。

Self-Debugging 的流程如下：

1. **生成**：LLM 根据任务描述生成初始代码。
2. **执行**：代码在沙箱环境中运行，收集执行结果——包括标准输出、标准错误、返回值、覆盖率信息等。
3. **解释**：LLM 阅读执行结果，用自然语言解释发生了什么（"在第 12 行，变量 `pivot` 未被定义就使用了"）。
4. **修正**：LLM 基于自身给出的解释，生成修正后的代码。
5. **迭代**：重复步骤 2-4，直到代码通过所有测试或达到最大迭代次数。

关键步骤是第 3 步。实验表明，当 LLM 被要求先"解释错误原因"再"生成修正"时，修正的成功率显著高于直接要求修正。这是因为自然语言的解释步骤充当了"思维链"，迫使模型在生成新代码之前先明确诊断问题，避免了盲目试错的低效模式。

Self-Debugging 是层级一改进的典型代表。它并不修改生成代码的智能体自身，但它展现了"生成-测试-修正"循环的强大威力。

值得指出的是，Self-Debugging 的思路可以自然扩展到更广泛的**执行反馈环路**。例如，在"Self-Repair"（自我修复）的扩展版本中，智能体不仅可以读取错误信息，还可以读取运行时性能特征（如内存占用、CPU 时间、API 调用次数），并基于这些特征推测性能瓶颈。在代码安全性领域，"自安全审计"变体让智能体先审计自己的代码是否存在安全漏洞（如 SQL 注入、缓冲区溢出），再对发现的漏洞进行修复。这些变体共享同一个核心范式：**将程序执行的副作用转化为可学习的反馈信号**。

回顾第二章的自我反思架构，Self-Debugging 可以被看作是反思回路的一个特化——反思对象从"任意自然语言输出"切换为"可执行代码"。这种切换看似简单，实则是一个质的飞跃：反思回路在自然语言领域的评估是模糊的、主观的（"这段回答是否逻辑清晰？"），而 Self-Debugging 的评估是精确的、客观的（"这段代码是否通过测试？"）。正是这种从"模糊评估"到"精确验证"的跃迁，使代码成为 RSI 的理想载体。

### 一个具体的伪代码示例

让我们通过一个具体的例子来感受这个循环。假设一个智能体的任务是实现一个快速排序算法：

```
# 第 0 轮：初始生成
def quicksort(arr):
    if len(arr) <= 1:
        return arr
    pivot = arr[0]
    left = [x for x in arr if x < pivot]
    right = [x for x in arr if x > pivot]
    return quicksort(left) + [pivot] + quicksort(right)

# --- 执行测试 ---
# 输入: [3, 1, 4, 1, 5, 9, 2, 6]
# 输出: [1, 2, 3, 4, 5, 6, 9]
# 错误: 列表中有一个重复的 1 被丢失了！
```

智能体（通过 Self-Debugging 的"解释"步骤）分析：`x > pivot` 的条件排除了等于 `pivot` 的元素。如果数组中有重复元素，与 `pivot` 相等的值会被丢弃。

```
# 第 1 轮：修正
def quicksort(arr):
    if len(arr) <= 1:
        return arr
    pivot = arr[0]
    left = [x for x in arr if x < pivot]
    middle = [x for x in arr if x == pivot]
    right = [x for x in arr if x > pivot]
    return quicksort(left) + middle + quicksort(right)

# --- 执行测试 ---
# 输入: [3, 1, 4, 1, 5, 9, 2, 6]
# 输出: [1, 1, 2, 3, 4, 5, 6, 9]  ← 正确！
# 但额外输入: [1]  → 输出: [1] ← 正确
#      输入: []  → 输出: [] ← 正确
#      输入（逆序）: [9, 8, 7, 6, 5] → 递归深度过大，栈溢出！
```

智能体再次分析：当输入是逆序排列时，`pivot = arr[0]` 总是选择最小值，导致每次分区都极不均衡——一侧为空，另一侧包含几乎全部元素。这是快速排序的最坏情况，递归深度达到 $O(n)$。

```
# 第 2 轮：优化
import random

def quicksort(arr):
    if len(arr) <= 1:
        return arr
    # 随机选择基准，避免最坏情况
    pivot_idx = random.randint(0, len(arr) - 1)
    pivot = arr[pivot_idx]
    left = [x for x in arr if x < pivot]
    middle = [x for x in arr if x == pivot]
    right = [x for x in arr if x > pivot]
    return quicksort(left) + middle + quicksort(right)
```

经过两轮"生成-测试-修正"，智能体不仅修复了重复元素的 bug，还优化了基准选择策略以应对最坏情况。整个过程不需要人类介入——错误信息充当了"环境反馈"，自然语言解释充当了"推理桥梁"，代码修改充当了"行动输出"。

### 从改进输出代码到改进智能体代码

上面的例子展示了层级一的改进——智能体在修正自己产出的排序代码。但智能体自身的代码（即驱动这个修正循环的提示词、逻辑和控制流）并没有改变。

现在考虑层级三：智能体能否改进驱动其自我调试过程的代码？假设智能体发现，在某些任务类别上，Self-Debugging 的"解释-修正"两阶段模式反而不如直接重写高效。于是它修改了自己的调试策略：

```
# 原始的调试策略（硬编码在智能体代码中）
def debug_loop(task, max_rounds=5):
    code = generate(task)
    for round in range(max_rounds):
        result = execute(code)
        if result.passed:
            return code
        explanation = explain_error(code, result)
        code = fix(code, explanation, result)
    return code

# 智能体自我改进后的调试策略
def debug_loop_v2(task, max_rounds=5):
    code = generate(task)
    for round in range(max_rounds):
        result = execute(code)
        if result.passed:
            return code
        # 新增决策分支：根据错误类型选择策略
        if result.error_type == "syntax":
            code = fix_syntax(code, result)  # 语法错误直接修，不需要解释
        elif result.error_type == "logic":
            explanation = explain_error(code, result)
            code = fix(code, explanation, result)
        else:
            code = regenerate(task, result)  # 复杂错误直接重写
    return code
```

注意这里的区别：第一段代码中，修正对象是任务代码（quicksort）；第二段代码中，修正对象是**调试策略代码本身**。智能体根据自己的历史经验（"语法错误时解释步骤是多余的"），重新设计了调试循环的控制流。

这就是 RSI 的本质——智能体的输出（元级决策）改变了智能体自己的运行时行为（对象级代码）。

很重要的一点是，层级三的改进是否能发生，取决于智能体是否**被授权**和**被装备**以修改自身的能力。在大多数当前的智能体部署中，智能体代码运行在一个与任务执行代码不同的权限域中——智能体可以自由读写任务目录，但不能修改自己的源代码目录。这种"自我写保护"是故意为之的安全设计。但讽刺的是，它同时也关闭了层级三 RS I 的大门。

要在安全性和自改进能力之间找到折衷，一个常见模式是**影子分支**（shadow branching）：智能体在一个独立副本上修改自己的源代码，将修改后的版本作为"竞争候选"与原版本并行运行，仅当候选版本在多轮评估中持续优于原版本时，才进行正式切换。这种模式借鉴了金丝雀部署（canary deployment）的思想——新版本先在小范围内验证，确认无害后再推广。

### 可验证性作为锚点

在层级三的改进中，一个核心风险是：智能体对自身策略的改进可能使系统变得更差，而不是更好。如何避免这种退化？

答案仍然在"可验证性"上。当改进的对象是智能体自身的代码时，我们可以使用一组**回归测试任务**来评估改进前后的性能。如果新策略在这些任务上的平均表现优于旧策略，则接受改进；否则回滚。

值得注意的是，回归测试的设计本身也可能被智能体改进——这就形成了一组交互进化的动态：测试集在进化，策略也在进化。如何防止两者同时退化（即"共谋"）是一个开放的研究问题。

### 自然语言提示与代码的边界消融

在 RSI 的实践中，一个有趣的现象是：代码和自然语言之间的边界正在变得模糊。现代 LLM 的提示词本质上是自然语言和结构化指令的混合体——它既不是纯代码，也不是纯文字，而是一种新形态的"软编程"。

当智能体在层级三中修改自己的提示词模板时，它修改的不是传统意义上的"代码"，而是自然语言中的结构化指令。这种修改的效力完全依赖于 LLM 遵循指令的能力——而这项能力本身也是可以被进化的（通过选择更有效的措辞、更精确的约束、更丰富的示例）。

这暗示了一个更宽广的图景：在 LLM 驱动的智能体系统中，**可改进的"代码"不限于传统编程语言**。任何可以被解析、修改并产生行为差异的文本结构——提示词、约束规则、知识图谱查询、工具调用描述——都是潜在的自改进对象。代码只是这类"可执行文本"中最精确、最可验证的子集。

### 代码作为"认知假体"

从更宏观的视角看，代码在 RSI 中扮演的角色类似于人类的**认知假体**（cognitive prosthesis）。人类通过写下笔记来扩展记忆，通过数学符号来扩展推理，通过编程语言来扩展计算能力。类似地，AI 智能体通过代码来扩展自己的自改进能力——代码将模糊的"改进直觉"转化为精确的、可执行的操作，使元认知不再停留在"想法"层面，而进入了"行动"层面。

这或许是人类和 AI 智能体在自我改进上最深刻的共同之处：我们都依赖外部表征（数学、语言、代码）作为思考的脚手架。区别在于，AI 智能体的外部表征可以直接返回机器执行并产生反馈，而人类的外部表征需要通过物理世界或社会互动来验证。这个闭环速度上的数量级差异，是 AI 自我改进可能远超人类自学速度的结构性原因。

## 本节小结

- 代码是 RSI 的天然介质，因为它同时具备可执行性、可验证性和可组合性，为"生成-测试-修正"循环提供了秒级的反馈效率。
- 代码自我改进有三个层级：改进输出代码（任务级）、改进工具代码（跨任务级）、改进智能体代码（元级），只有第三个层级触及 RSI 的理论核心。
- Self-Debugging 方法展示了"解释-修正"两阶段模式的有效性，其核心洞察在于自然语言的解释步骤充当了思维链，显著提高了修正成功率；这一模式可扩展到自安全审计和性能自优化等变体。
- 现代 LLM 系统中，可改进的"代码"不限于传统编程语言——提示词、约束规则、工具调用描述等任何可被解析并产生行为差异的文本结构都是潜在的自改进对象。
- 可验证性（回归测试）是层级三改进的安全锚点，影子分支策略提供了在安全性和自改进能力之间的折衷方案。
