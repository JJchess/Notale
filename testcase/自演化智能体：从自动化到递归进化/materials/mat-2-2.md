## 自我反思循环：生成→评估→修正的闭环设计

上一节我们看到了 LLM 如何让"反思"从科幻概念落地为工程现实：语言本身成为了可搜索、可操作、可修正的媒介。但一个单次的"输出—批评—改进"序列还远不足以构成一个完整的自演化系统。真正的问题在于：**我们如何将这个反思机制结构化为一个可重复、可收敛、可泛化的闭环？**

这一节将回答这个问题。我们从抽象的架构组件入手，然后深入两个里程碑式的算法——Reflexion（Shinn et al., 2023）和 Self-Refine（Madaan et al., 2023），最后用一个完整的运行示例来展示这个闭环如何在实际中运转。

### 三个核心组件：生成器、评估器、修正器

无论具体的实现如何变化，任何一个自我反思系统都可以被分解为三个功能组件：

**生成器（Generator）** 是系统的"表达层"。它接收当前的任务描述、历史上下文以及任何已有的反馈信息，然后生成一个候选输出。生成器就是那个"做事"的模块——它写出代码、给出答案、生成计划。在 LLM 驱动的系统中，生成器通常就是一个被赋予特定角色和指令的语言模型。它的核心输入是任务 $T$ 和当前可用的上下文 $C_t$，输出是一个候选解 $s_t$。

**评估器（Evaluator）** 是系统的"判断层"。它接收生成器的输出 $s_t$，然后判断这个输出在多大程度上满足任务目标。评估器可以是以下几种形式之一：

- **外部信号评估**：利用真实世界的反馈——代码是否通过了单元测试、生成的文本是否命中了某个评分标准、智能体是否在环境中获得了奖励。这种评估噪声低、信号真实，但并非所有任务都能提供这样的外部 oracle。
- **LLM 自评估**：用一个（可能不同的）LLM 对输出进行打分和批评。这在开放式任务（如写作质量、论证逻辑）中极其有用，因为这类任务没有简单的标量指标。但自评估也引入了新的挑战——LLM 可能对自己的输出过度宽容，或产生幻觉式的批评。

**修正器（Refiner）** 是系统的"改进层"。它接收评估器的反馈 $f_t$，连同原始任务和历史上下文，然后对输出进行有针对性的修正。修正器并不从头开始生成——它以上一轮的输出为基础，进行增量的、定向的改进。修正器的核心智能在于**理解反馈并转化为具体的修改操作**。

这三个组件的关系可以用如下流程图表示：

```
任务 T → [生成器] → 候选解 sₜ
                       ↓
                  [评估器] → 反馈 fₜ
                       ↓
                  [修正器] → 改进后的解 sₜ₊₁
                       ↓
                  [评估器] → ... (循环)
```

需要注意的是，评估器和生成器可能共享同一个 LLM，也可能使用不同的模型实例。在大多数实际系统中，生成器和修正器是同一个 LLM，只是被给定了不同的提示指令——生成时强调创造力，修正时强调针对性。

### Reflexion：带着记忆反思

Reflexion（Shinn et al., 2023）是这个领域中具有里程碑意义的工作。它的核心洞察是：**反思不应该只是单轮的批评—修正，而应该将过去的反思持久化，形成一种"反思记忆"来指导后续的生成。**

Reflexion 最初被设计用于决策型任务——智能体在 HotPotQA 问答、HumanEval 编程和 ALFWorld 具身交互等环境中行动。它的架构包含三个关键角色：

**行动者（Actor）** 就是我们的生成器，它在环境中执行动作。**评估器（Evaluator）** 判断行动的结果——在编程任务中，评估器利用单元测试的通过/失败信号；在问答任务中，评估器比较答案与标准答案；在具身环境中，评估器检查任务是否完成。

但 Reflexion 的真正创新在于第三部分：**反思记忆（Reflection Memory）**。当行动者失败时，系统会要求 LLM 生成一段"反思"——这不是对输出的修正，而是对失败原因的**口头分析**，例如：

> "在上一次尝试中，我错误地使用了 `str.split()` 而没有处理标点符号，导致词频计数不准确。下次我应该使用正则表达式或 `string.punctuation` 进行预处理。"

这段反思会被**持久存储**到一个专门的内存空间中。在后续的生成中，这段反思会作为额外的上下文输入给行动者。理论上看，这相当于用自然语言实现了一种**经验回放（experience replay）机制**——过去的错误以语义压缩的形式被记住和复用。

关键的是，Reflexion 的反思不是对输出的一次性修正，而是对**元认知策略**的记录。它不直接说"代码应该改成这样"，而是说"我之前犯了这类错误，下次需要注意这类问题"。这种元认知层面的表述具有更强的泛化能力——同一条反思可以指导未来多种不同情境下的类似问题。

Reflexion 在多个 benchmark 上展现了显著提升。在 HumanEval 编程任务上，Reflexion 将 GPT-4 的 pass@1 从 67.0% 提升到 88.0%；在 HotPotQA 问答上，准确率提升了约 20 个百分点；在 ALFWorld 具身任务上，成功率从约 60% 提升到超过 90%。

### Self-Refine：迭代自修正的无记忆范式

与 Reflexion 同一时期，Madaan 等人提出了 Self-Refine。如果说 Reflexion 的核心创新是"记忆"，Self-Refine 的核心创新则是**"反馈的细粒度"与"迭代的即时性"**。

Self-Refine 的流程极其简洁：

1. **生成（Generate）**：LLM 生成一个初始输出。
2. **反馈（Feedback）**：同一个 LLM 对输出进行多维度的质量审查——它会在自然语言中指出具体的问题区域、问题的性质，以及为什么需要修改。
3. **修正（Refine）**：LLM 基于这些反馈直接修改输出，产生一个改进版本。
4. **迭代（Iterate）**：将修正后的输出再次送入反馈阶段，循环直至满足停止条件。

Self-Refine 与 Reflexion 最关键的差异在于：**Self-Refine 不维护跨轮次的显式记忆**。每一轮的修正直接以前一轮的输出和反馈作为输入，不做语义压缩或持久化。这使它更加轻量和易于部署——你不需要设计记忆的存储结构和检索策略——但代价是它无法累积跨任务的经验。

Self-Refine 的停止条件通常有两种：（1）达到预设的最大迭代轮次，或（2）LLM 在反馈阶段自行判断"当前输出已经没有需要改进的地方"。

Madaan 等人在多种任务上验证了 Self-Refine 的有效性。在对话生成任务上，多次迭代将质量评分从 58.6 提升到 78.9；在代码优化任务上，运行时间中位数下降了约 30%；在数学推理任务上，准确率有稳健但渐近的提升——通常在 3-4 轮迭代后趋于饱和。

### 两种范式的对比

Reflexion 和 Self-Refine 代表了自我反思系统的两条设计路线。它们的差异反映了设计者对"反思"本质的不同理解——Reflexion 认为反思的核心价值在于**跨时间的泛化**（一条反思指导多个未来场景），Self-Refine 则认为反思的核心价值在于**当下的深度**（对当前输出进行多维度、细致的打磨）。

| 维度 | Reflexion (Shinn et al.) | Self-Refine (Madaan et al.) |
|------|--------------------------|------------------------------|
| **记忆机制** | 显式持久化：反思文本存储在"反思记忆"中，跨轮次保留 | 无持久记忆：每轮仅以前一轮的输出+反馈为上下文 |
| **反馈粒度** | 宏观：对方法论的元认知反思（"我以后再遇到这类问题时应该……"） | 微观：对输出的具体问题点评析（"第三段的论证缺少数据支撑……"） |
| **停止条件** | 成功执行（通过测试/达成目标）或达到最大尝试次数 | LLM 自评"无需再改"或达到最大迭代轮次 |
| **适用场景** | 决策型任务（编程、问答、具身交互）——有明确的成功/失败信号 | 生成型任务（文本写作、对话、代码优化）——质量是连续谱 |
| **跨任务迁移** | 强：反思记忆是元认知性的，可在相似任务间复用 | 弱：不维护跨任务记忆，每次从头开始 |
| **工程复杂度** | 较高：需要设计记忆存储、检索和注入机制 | 较低：只需串行管道，无状态管理 |

这两种范式并非互斥。一个完整的自演化系统完全可以在细粒度迭代修正（Self-Refine 风格）的同时，将高层次的失败经验总结为反思记忆（Reflexion 风格）。理解这两种范式，就等于掌握了反思架构设计的两条正交轴——**纵轴是对当前任务打磨的深度，横轴是对历史经验复用的广度**。

### 一个完整的反思周期：从代码错误到正确的执行跟踪

让我们用 Reflexion 范式走一个完整的周期，在 HumanEval 风格的任务中追踪数据流和状态变化。任务是：**编写一个函数，判断一个整数数组是否可以被重新排列为等差数列。**

---

**第 0 轮：初始生成**

输入（Actor 的 prompt）：
```
Task: Write a function `can_make_arithmetic_progression(arr)` that
返回 True 如果 arr 重新排列后可以构成等差数列。

Previous reflections: (none)
```

输出（Actor 生成）：
```python
def can_make_arithmetic_progression(arr):
    if len(arr) <= 2:
        return True
    diff = arr[1] - arr[0]
    for i in range(1, len(arr) - 1):
        if arr[i+1] - arr[i] != diff:
            return False
    return True
```

*评估器判定：FAIL。原因——函数假设数组已经排序，但 arr 是任意顺序的。*

---

**反思生成**

LLM 被要求基于失败分析生成反思：

> "我假设了输入数组已经按等差顺序排列，但题目要求判断的是'重新排列后'是否能构成等差数列。我应该先将数组排序，然后再检查相邻元素的差值是否相等。这是一个关于输入顺序的假设错误。"

这条反思被存入反思记忆：`reflection_memory = ["假设了输入已排序，需先 sort"]`

---

**第 1 轮：带反思的生成**

输入（Actor 的 prompt）：
```
Task: Write a function `can_make_arithmetic_progression(arr)` that
返回 True 如果 arr 重新排列后可以构成等差数列。

Previous reflections:
- 假设了输入已排序，需先 sort。重新排列意味着我们可以任意调整顺序，所以应该先排序再检查。
```

输出（Actor 生成）：
```python
def can_make_arithmetic_progression(arr):
    arr_sorted = sorted(arr)
    diff = arr_sorted[1] - arr_sorted[0]
    for i in range(1, len(arr_sorted) - 1):
        if arr_sorted[i+1] - arr_sorted[i] != diff:
            return False
    return True
```

*评估器判定：PASS（所有测试通过）。*

---

这个三步骤周期清晰地展示了反思记忆的价值：一条高度压缩的自然语言提示（"需先 sort"），携带了从失败经历中提炼出的语义知识，在下一轮中直接指导了正确的代码结构。这正是 Reflexion 的核心循环——**失败 → 语义反思 → 记忆注入 → 改进生成**。

## 本节小结

- 自我反思闭环由三个标准组件构成：生成器（产生候选解）、评估器（判断质量）、修正器（基于反馈改进）——三者串行形成反馈回路。
- Reflexion（Shinn et al., 2023）的核心创新在于将元认知反思持久化为"反思记忆"，实现了跨轮次甚至跨任务的经验复用，在编程和决策型任务上取得了显著提升。
- Self-Refine（Madaan et al., 2023）采用无记忆的迭代自修正策略，通过多轮"反馈→修正"对话在生成型任务上持续打磨输出质量。
- 两种范式反映了反思设计的两条正交轴：纵轴是对当前输出的迭代深度，横轴是对历史经验的迁移广度。
